# 計画（案）：振替休日の［休む日を出勤に変える］で、時間も変えられるようにする（2026-10-27）

## きっかけ（ユーザー）
- 振替休日（大掃除の振替）の休む日を在宅に変えたい、という依頼がスタッフから来た。
- 今は「いつもどおり」か「いつもと違う場所」しか選べず、場所を変えたときも**時間はいつものシフトのまま**の勤務地変更が作られる。
- 「通常はこうだけど、どう変更するか」を入れたい。

## 案（ユーザーに見せたモック・2026-10-27）
- 休む日の勤務：［いつもどおり］［時間・場所が違う］（2択に）
- ［時間・場所が違う］を押すと：
  - 「いつものシフト：9:15〜17:00　四条本校」（休む日の normal_shift）
  - 「この日の勤務時間」開始〜終了（**最初はいつものシフトが入っている**）
  - 「勤務地」（いつもの校が入っている・校の一覧＋その他（自由入力））
  - いつものシフトと比べて、種別は今の残業申請と同じ決まりで自動（lib/overtimeSubmit の detectOvertimeTypes／composeApplicationTypes）：
    始まりが遅い→遅出の理由（LATE_CHOICES・時間調整／短期・イベント／練習・試合／会議・大掃除／出張・在宅／遅刻）、
    終わりが早い→早退の理由（EARLY_CHOICES）、始まりが早い→早出、終わりが遅い→残業、場所が違う→勤務地変更
  - 青い枠「休む日 11/5（水）に作る申請：遅出（会議・大掃除など）・勤務地変更（在宅） 13:00〜17:00／合計時間数：−3:45」
  - 送るボタンのすぐ上に「申請先：◯◯さん（役職）」（自己受理なら出さない or 「自己受理」）
- **2本シフト（例 9:15〜12:30／14:00〜17:00）の方も、入れる時間は1つ（開始〜終了）だけ**（2026-10-27 ユーザー確定 案A）。休憩はふだんどおり自動（lib/breakCalc）

## 作り方の案
- DB（migration）：
  - overtime_reports に列 furikae_change_plan jsonb（休む日に作る申請の中身：start・end（分）・break_minutes・labor_minutes・diff_minutes・application_types・late_situation・early_situation・location）。null＝今までどおり（場所だけ／いつもどおり）
  - trg_furikae_report_state：本人に書き換えさせない列に足す（本番の実定義から）
  - furikae_change_apply（本番の実定義から）：③ を「plan があれば plan の中身で1件（種別は plan の application_types）」に。plan が無ければ今までどおり
  - 種別は許す一覧（overtime・early_start・late_start_adj・tardiness・early_end_adj・early_leave・location_change）だけ。時間は 0〜1440、終了＞開始。ここで止める
  - 時間が同じ・場所も同じなら「いつもどおり」と同じ（申請を作らない）
- Edge Function overtime-approve：action 'furikae_change' で change_plan を受け取り、形を確かめて列に入れる。差し戻しで plan も消す。受理（approve）の流れは今のまま（apply が plan を読む）。ベル・カレンダーの同期は今のまま（できた申請を同期）
- 画面：OvertimePage の窓。計算は今の残業申請と同じ部品（detectOvertimeTypes・composeApplicationTypes・breakCalc・effectiveLocationOf）を使う。lib/timeInput を通す
- 受理する人の画面（受理ページの「振替休日の変更」の枠）：休む日 → 「遅出・勤務地変更（在宅）13:00〜17:00（−3:45）」を出す
- 社内FAQ：答え 3442d31e の【休む日に出勤することになったとき】に1文

## 気になっていること（レビューで見てほしい）
1. 計算（休憩・労働時間・差分・種別）を画面で作って送り、DB はそのまま入れる形でよいか（ふだんの残業申請も画面が計算して insert している）。サーバーで計算し直すべきか
2. 遅出・早退の理由の選択肢を窓の中に出すと長くなる（スマホ）。出し方
3. 休む日がもう過ぎている（あとから変更）とき、作る申請は確認済み（実績）になる。時間を入れさせてよいか
4. 休む日のシフト調整の相談（shift_adjust）：遅出・早退で「いない時間」ができる。今の (307) の仕組み（ot_partial・shift_adjust_needed）はこの経路で作った申請にも効くか
5. 振替元の日の休日出勤の時間は今までどおり（振替休日の申請に入っている振替元の時刻）。こちらは変えない
6. 文言（「時間・場所が違う」「この日の勤務時間」「休む日に作る申請」）

## レビュー（UI/UX・シニアエンジニアの2体・2026-10-27）と裏取り
### 🚨 直さないと壊れる（自分でコードを見て確かめた）
1. 2本シフトで「入れる時間は1つ」（案A）のままだと、何も変えずに送っても差が出る：
   いつも 9:15〜12:30／14:00〜17:00（労働 6:15）→ 1つの 9:15〜17:00 は休憩が自動で 45分（lib/breakCalc の calcSegmentBreak・13時より前に始まり 6:30〜8:45）＝労働 7:00 → 差 +0:45（種別は空のまま）。
   「時間が同じなら作らない」でも同じと判定されない。→ 2本シフトの扱いをユーザーに聞き直す
2. シフト調整の相談が付かない：apply の①（振替休日の取消）で相談は「休みが取り消されました」になり、あとから入れる遅出・早退の行は shift_adjust_needed=false
   （trg_zz_shift_adjust_pt_ins は when (new.shift_adjust_needed)・20261020202207 の165行）。受理の画面の「シフト調整：必要／調整不要」も変更の依頼では出していない（OvertimePage 4596行 !furikae_change_requested_at）。
   → 受理の画面と自己受理の窓に「シフト調整：必要／調整不要」を出し、apply が insert で shift_adjust_needed を入れる（今の「場所だけ」の経路も同じ穴）
3. 古い画面（端末の写し）の受理者が、時間の変更を見ないまま受理できる → plan がある依頼の受理は、新しい画面だけが送る印が無ければ 409「画面を更新してください」
4. plan の付け外しを全部の経路に（印を付ける update・自己受理の失敗の戻し・差し戻し・trg_furikae_report_state の本人の書き換え止め）
### 直したほうがよい
5. plan には入力だけ（start・end・location・late_choice・early_choice）を持たせ、休憩・労働・差分・種別は apply が r.normal_shift から計算（calcSegmentBreak の SQL 版）。画面は表示用に同じ計算
6. 過ぎた日は確認済み（実績）になる → 窓と受理の画面に「休む日が過ぎているため、実績として記録されます」
7. plan があるのに normal_shift が空なら、黙って飛ばさずエラー
8. 「合計時間数」が2つの意味になる → 上の行は振替全体（振替元の労働＋休む日の差）、青い枠は「休む日の通常シフトとの差」。受理の画面・お知らせ・履歴の文も plan に合わせる
9. 「時間・場所が違う」を選んで何も変えていない → 欄の下に「通常シフトと同じです。［いつもどおり］を選んでください」・送れない。終了が開始より前 →「勤務時間の入力を確認してください」。エラーは各欄の下にも
10. 理由の選択肢はふつうの申請と同じ形（2列・全部出す・遅刻だけ横長）。「ほか…」で畳まない。開始を通常に戻したら遅出の理由を消す・［いつもどおり］に戻したら時間などを送らない
11. 言葉：「いつものシフト」→「通常シフト」／ボタン「時間や場所が違う」／「休む日 11/5（水）は、次の内容になります」＋種別の札（TypeChips）／自己受理は「自己受理のため、押すとすぐに変わります」

## ユーザーの決定（2026-10-27）
- 2本シフトの方だけ時間の欄を2つ（最初は通常シフトの2本が入る・片方を消せば1つ）。1本シフトの方は1つ。何も変えなければ差 0:00（上の 1. は解消）
  → plan の入力は segments（1〜2個の start・end）・location・late_choice・early_choice。休憩は今の残業申請と同じ（帯ごとの calcSegmentBreak）
