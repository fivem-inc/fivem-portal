## A：設定（app_settings）の読み込みを1回にまとめる
- 新しい部品 `lib/appSettings.ts`：`getAppSetting(key)`／`getAppSettings(keys)`
  - 同じ瞬間（同じ処理の流れ）に頼まれたキーは **1回の問い合わせ**（`.in('key', [...])`）にまとめる
  - 読めた値は **10分** 使い回す（画面の中＋端末の localStorage。🚨 ログアウトの localStorage.clear で消えてよい）
  - 🚨 自分が app_settings を書いたら（管理画面の保存＝lib/writeWatch が見ている）、すぐ捨てて読み直す（「自分の操作はすぐ」）
  - 読めなかったときは今までどおり（呼ぶ側の既定値・null）。失敗を使い回さない
  - 起動のときに、どの画面でも使うキー（idle_logout・feature_published など）をまとめて先に1回読む
- 置き換える所（読むだけ。書く所は変えない）：lib/overtimeUnify（2つ）・lib/idleLogoutConfig・lib/tripPending・lib/pushBannerConfig・lib/overtimeSubmitApi（furikae_report_on）・lib/gcalCalendarConfig・pages/BoardPage（4つ）・lib/encouragementExempt・lib/staffLeave・lib/studySessionsApi・hooks/useFeaturePublished・hooks/useAdminAccess（中身を見て当てはまるものだけ）
- 🚨 DB の側の守り（区切りの日など）は DB が自分で読むので、画面の値が最長10分古くても、守りは今までどおり
- 見込み：app_settings 1,699 → 200〜300/日

## B：よく読むものを、しばらく使い回す（他人の変更が出るまで最長10分）
- 決まり（2026-10-19 からの方針・メモリ「自分の操作はすぐ反映」）：他人の操作の反映は10分まで遅れてよい／自分の操作はすぐ
- B1 役職の一覧（hooks/useRoles）：今は画面の中だけ10分＝アプリを開き直すたびに読む → 端末にも10分持つ（localStorage の 'fivem_roles_cache' はもうある＝起動の表示用。新しさの印を足す）。roles?name=eq.管理者（40）も同じ部品に寄せる
- B2 本人のプロフィール（hooks/useAuth）：開き直すたびに読む → 端末の控え（AUTH_CACHE）が10分以内なら、それで済ませる（🚨 退職・休職・権限の変更は今でも最長10分。AuthContext の在籍の確認（my_access_state）は今までどおり毎回）
- B3 連絡板の全員の一覧（BoardPage の profiles・166）：10分使い回す
- B4 安否確認（hooks/useSafetyPendingCount・697）：🚨 緊急の知らせなので遅らせない。出し方は変えず、安否確認が送られたときに必ず作られるベル／スマホの行（notifications の目印）をきっかけに読み直す形にして、それ以外のときの読み直しを減らす（今どの時点で読んでいるかを調べてから決める）
- B5 お知らせの目印（lib/badgeLedger）：今は見えている間3分ごと → **変えない**（数字が増えるのが遅れるため）。どこで重なって読んでいるかだけ調べる
- 見込み：B1〜B3 で 400〜600/日、B4 次第で＋数百

## 確かめ方
- 画面：tsc・build・lint／手元で、開き直し・ページの移動・前面に戻したときに、読む回数が減ったか（ブラウザの通信の一覧で数える）
- 自分の操作がすぐ出るか：管理画面で設定を変える→同じ端末ですぐ変わる／安否確認を送る→相手の画面にすぐ出る（試しの宛先は管理者だけ・お知らせが他の人に飛ばない形で）
- 本番に出したあと：Logs Explorer で同じ問い合わせをして件数を比べる（ふつうの平日で）

## 気になっていること（レビューで見てほしい）

2. B2 で「開き直しても10分は前の権限」が、退職・休職・権限を外したときの守りを弱くしないか（DB の RLS が最後の守りであることの確認）

4. ほかに、もっと効く所（overtime_reports・board_messages・leave_requests・my_home_feed など）で、同じ形で減らせるもの

## レビュー（シニアエンジニア・UI/UX と運用の2体・2026-10-28）と裏取り・直した計画
### 2体とも同じ意見（自分でコードを見て確かめた）
- 🚨 **端末（localStorage）に10分持つのはやめる**：lib/writeWatch の「自分が書いた」の記録は画面の中だけ（開き直すと消える）＝管理者が保存して開き直すと古い値が出る・「開き直せば最新」の逃げ道も消える。
  → A・B とも **画面の中だけ**で使い回す（今の useFeaturePublished・useRoles・useAuth と同じ形）。件数は「最初にまとめて1回読む」だけで目標に届く
- B4 安否確認：ベルをきっかけに読み直す形は**もう入っている**（hooks/useSafetyPendingCount の useRefreshOn）。多いのは key が無く、ページを移るたび・ナビ／ホーム／連絡板で別々に読むため。
  安否確認の Edge Function はベルの insert の error を見ていない＝ベルだけに頼らない → **10分にしない**
### 直した計画
- A：lib/appSettings（画面の中だけ）。最初の呼び出しで、よく使う鍵をまとめて1回（.in）。同じ瞬間の頼みは1回に。10分。自分が書いたら捨てる。
  「読めなかった」と「行が無い」を分けて返す（失敗は前回の値を保つ呼ぶ側がある）。ログインしていないときは作らない・人が変わったら捨てる。timeoutSignal。管理画面の設定の読み込みは通さない（別の管理者の変更を古い値で上書きしないため）
- B1：useAuth の fetchPermsForRole が毎回 roles?name=eq.<役職名> を引いている（useAuth.ts:160）→ profiles を読むときに role_id も読んで、この1本をやめる（約186件/日・確実）
- B2：使い回しにしない。（できれば）AuthContext が毎回読む profiles（is_active）に本人の表示の列を足して1本に → 🚨 2人共通の AuthContext・useAuth に触るので、場所予約の担当へ連絡。touch_last_sign_in（最終アクセス）は残す
- B3：連絡板の loadAll のうち変わりにくい7本（全員の一覧・master_options・board_can_manage_groups・設定4つ）だけを画面の中で10分使い回す（送ったあとの読み直しでは使い回す）
- B4：進行中の安否が手元にある間は今どおり。無い間だけ同じ瞬間の読み込みを1本にまとめ、ページを移ったときは90秒以内なら読まない
  - 🚨 2026-10-28 試しで戻した：届いた直後（90秒以内）にページを移っても出ず、最長3分遅れた。安否確認は遅らせないので B4 はやらない（ユーザー確定）
- 追加（もっと効く所・確認済み）：
  ・ホームを開くたびに home_mark_seen の書き込みで 'home' の話題が立ち（writeWatch の ^home_）、my_home_feed をもう1回読んでいる → home_mark_seen を IGNORE に（画面は markSeenLocal で直っている）
  ・ホームのバナー（App.tsx の notifications）に key が無く、開くたびに読む → key を付ける（🚨 App.tsx は2人共通）
  ・useLeavePendingCount が1つの数字のために3本 → 1本に
- やめたこと：B5（お知らせの目印）は変えない。C（cron の間隔）は保留。パソコンの開きっぱなしの3分ごとを休ませる案は保留（要相談）
- 見込み（推測）：A で 1,699→250〜400／B1 −186／ホームの2回目 −200〜400／B3・B4・バナー・休暇の数で −500〜1,000。合わせて 1日 −2,500〜3,500 件（API の入口の 12〜16%）
