# 計画：パートの方の「予定どおりの出張」には勤務変更の下書きを出さない（2026-10-24 ユーザー確定 案A・レビュー前）

## きっかけ
- 出張報告（到着・終了）を送ると、その日の申請の下書き（「📋 出張の申請がまだの日」）ができる。パートの方は勤務変更、それ以外は残業申請。
- パートの方は、登録シフト（weekly_shift_patterns）の中にもともと出張先が入っている日がある
  （例：火曜 10:00〜18:00「四条本校→JEUGIA 四条→四条本校」）。この日はシフトどおりの勤務なので勤務変更は要らないが、下書きが出て「まだの日」に残り続ける。
- 「勤務時間の中なら出さない」だけにすると、シフトの時間中にイベントなど予定に無い所へ行った日も消えてしまう（ユーザー指摘）。

## これまでの実績（2026-05-31〜10-24・本番で数えた）
- パートの方の出張の日は2日だけ。
  - 10/20（火）：到着 12:35（終了の報告なし）・登録シフト 10:00〜18:00、勤務地に出張先が入っている・勤務変更は出していない → この案で下書きが出なくなる
  - 10/11（土）：その曜日はシフトなし・休日出勤を提出済み → この案でも今までどおり出る
- 参考：正社員の方（残業申請）は、勤務時間の中の8日のうち3日で申請が要った（早退・残業・勤務地変更）。だから正社員の方には入れない（ユーザー確定）。

## 決まったこと（ユーザー確定）
- 対象はパートの方（勤務変更の下書き）だけ。正社員の方の残業申請の下書きは今までどおり。
- 案A：次の①と②の両方を満たす日だけ、下書きを出さない（「まだの日」に出さない）。
  - ① 出張先が予定に入っている：
    - 登録シフト（その日に有効な行）の勤務地（「→」で区切った各校）に、出張報告の行き先が入っている、または
    - 決定済みのシフト表（大人の「出張」・こどもの「園指導」）に、その日その人の出張として載っていて、行き先が同じ
  - ② 出張報告の時刻（到着・終了のうち、その日にある方）が、登録シフトの時間（最初の開始〜最後の終了）の中にある

## 作り方（案）
- DB の関数 `my_trip_pending_days` だけを直す（「まだの日」はここ1か所で決まる。出張報告の画面・勤務変更のページ・残業申請はこれを読むだけ）。
  - 🚨 本番の実定義から起こす。`v_form = 'shift_report'` の枝に「予定どおりなら出さない」を足すだけ。残業申請の枝は触らない
  - 登録シフトの探し方は `overtime_confirm_trip_rostered` と同じ（company_calendar で休館日・社員出勤日を見て day_kind を決める・その日に有効な行）
    - 🚨 画面の resolveNormalShift には「社員出勤日に『出』の行が無ければ曜日の行」の決まりがある（sync_overtime_from_leave も同じ）。DB でもこれに合わせるか要確認
  - シフト表の照合は `overtime_confirm_trip_rostered` と同じ（kids_shift_items・cells・places・people、行き先は trip_location_id と出張報告の location_option_id）
  - 出張先の名前の比べ方：出張報告の location（文字）と登録シフトの location を「→」で分けた各校を、空白を除き NFKC で比べる（`overtime_confirm_trip_rostered` の比べ方と同じ）
  - 泊まりがけ（span_start ≠ span_end）は対象外（今までどおり出す）
  - 到着・終了のどちらも無い日（泊まりの途中の日）は対象外（今までどおり出す）
- 画面：文言の追加・変更。どこに何を書くかはレビューで決める（候補：勤務変更のページの説明の1行・出張報告の画面の説明・社内FAQ 2件）
  - 出張報告を送ったあとの「本日の勤務変更の下書きを作成しました」は、「まだの日」に今日が入ったときだけ出る作りなので、自動で出なくなる
- 社内FAQ：答え 0d8a4c3b・9b3e5f71 に「パートの方は、登録シフトどおりの出張で時間内なら下書きはできません」を足す（文は案を出して確定）

## 気になっている点（レビューで見てほしい）
1. 到着だけ・終了だけの日（10/20 は到着だけ）。到着がシフトの時間内でも、実際はシフトの終わりを過ぎて働いていたかもしれない。終了を送り忘れた日は、下書きが出ないまま残業（勤務変更）を出し忘れるおそれ
2. 到着を送った時点では「まだの日」に出ず、あとで終了を送るとシフトの終わりを過ぎていたので出る、という出たり消えたりの動き
3. 本人に「なぜ出ないのか」が分からない。出ないことの説明をどこに・どれだけ書くか
4. 出張先の名前の照合が文字なので、表記ゆれ（「JEUGIA四条」と「JEUGIA 四条」など）で外れる
5. 登録シフトの時間とシフト表の時間が違う日・社員出勤日など特別な日の扱い
6. 確認者（受理する人）の側から見て、出張の日に勤務変更が無いことが分かるか（困るか）

## レビューの結果（2026-10-24・UI/UX デザイナーとシニアエンジニアの2体・大事な指摘は本番で裏取り済み）
技術の決まり（ユーザーの判断は要らない）
- 判定は `trip_days_of` の1行ずつにかけ、そのあとで distinct on する（同じ日に予定どおりと予定外の2組があるとき、予定外の組を残すため）
- 時間帯は `least(start_time, start_time2)`〜`greatest(end_time, end_time2)`（帯2が朝の行が本番に5行ある・画面の normalShiftBands と同じ）。時刻は分にそろえて両端を含めて比べる
- 日をまたぐシフト・労働時間0・start_time が空の日は「予定どおりではない」＝下書きを出す側に倒す
- 行き先は ID で比べる：登録シフトの勤務地を「→」で分け、各校を master_options（trip_location_*）の value で ID に直して出張報告の location_option_id と比べる（20261020171645 から勤務地は master_options の value と同じ文字でないと保存できない）。手入力の行き先（location_option_id が空）は対象外＝出す
- 登録シフトは「その日に有効な行だけ」で探す（画面の findPatternRow のように近い期間の行は使わない）。社員出勤日に「出」の行が無ければ曜日の行（overtime_confirm_trip_rostered の本番の定義と同じ・確認済み）
- 判定は内部用の関数に出す（例 registered_shift_of・trip_day_on_roster。anon・authenticated から revoke）。overtime_confirm_trip_rostered の置き換えは次の段（本番の実定義と差分を取ってから）
- my_trip_pending_days の戻りの形は変えない（読んでいる画面が4か所）。本人への説明が要るなら、その日の状態を返す関数を別に作る
- 勤務変更のページの ?trip= で一覧に無い日を一律「勤務変更はすでにあります」と出している → 報告済みの日だけその文、それ以外は別の文
- 勤務変更のページで「まだの日」が読めなかったとき console だけ → 画面に出す（前からの穴）

ユーザーに決めてもらうこと
1. 時刻の幅：シフトの少し前に到着する・少しあとに終了を送るのはふつう。どこまで「時間内」とするか
2. 到着だけで終了を送っていない日：下書きを出さない（10/20 はこれ）か、出すか
3. 区分：「出張」「園指導」のときだけ消す（試合・イベント下見・その他はいつも出す）か
