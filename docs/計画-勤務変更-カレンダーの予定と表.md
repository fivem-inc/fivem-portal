# 計画：勤務変更に「上長が入れた勤怠カレンダーの予定」と［カード｜表］（2026-11-05・案・未着手）

## きっかけ（ユーザーの要望）
- パートの方は勤務変更の「履歴」しか見られない。上長が勤怠カレンダーに入れた予定（欠勤・遅刻・早退・勤務地変更・休日出勤・時間変更）が、自分の側でどうなったか見られない
- 同じ画面で区分けして見たい／上長が書いた予定から、そのまま勤務変更の報告を出したい／残業申請と同じ［カード｜表］
- 最初は権限でマネージャー以上だけ → 確かめてからパートに公開
- いずれは残業申請と同じ「事前申請 → 受理 → 実績報告」の流れにしたい（今回は作らない・土台だけ考える）
- あわせて：休暇申請・残業申請の2段のタブの上下を入れ替える（オレンジの［受理待ち／確認待ち｜申請の依頼］を上、緑の自分のタブを下）

## 今の作り（調べた結果）
- 勤務変更（client/src/pages/ShiftReportPage.tsx）：タブは［✏️ 報告］［📋 履歴］の2つ。履歴は fetchMyReports（shift_reports の本人の分・状態の絞り込みあり）
- すでに「カレンダーの予定から報告を作る」一覧がある：components/ShiftReportTodo.tsx＋lib/shiftReportTodo.ts の buildTodo（「報告」タブの中・権限 shift_report_todo＝今はマネージャー以上と管理者だけ）。
  attendance_exceptions の本人の行を読み、先の日・締め（支給月17日）を過ぎた日・同じ勤務日の報告が1件でもある日は出さない。押すと pickTodo で種類・時刻・場所を入れた状態でフォームが開く（TYPE_MAP：absent→欠勤・late→遅刻・early_leave→早退・holiday_work→休日出勤・location_change→勤務地変更・time_change→本人が選ぶ）。承認者はパートの方を選んで見られ、送ると代理報告
- 勤怠カレンダーの予定＝attendance_exceptions。本人は自分の行を読める（RLS）。🚨 報告とのつながりの列は無い（applicant_id＋work_date が同じかだけ・shift_reports は (applicant_id, work_date) で一意）
- 残業の［カード｜表］の部品は OvertimePage.tsx の中に閉じている（useOtTableMode・OtViewSwitch・fillAllDays・OtBackToTable・OtDayWrap はそのまま出せる。OtHistoryTable・OtPeriodBar は残業の型と残高に依存）。日ごとにまとめる部品は components/DayFrameList に共用済み
- 状態：残業 requested→request_confirmed→reported→confirmed（＋returned・cancelled）／勤務変更 pending・resubmitted・confirmed・cancelled・returned（事前と実績の段が無い）

## 案

### 段0：2段のタブの上下を入れ替え（休暇申請・残業申請）
- LeaveRequest.tsx・OvertimePage.tsx で ManagerTabs を PageTabs の上に（JSX の順だけ）。下の枠の角（'0 0 12px 12px'）は PageTabs のすぐ下のままなので変えない。ManagerTabs の上下の余白を合わせる
- 勤務変更は2段目がまだ無い（［確認ページへ］ボタンだけ）→ 段1 で同じ形にそろえるかは別に決める

### 段1：勤務変更の履歴に「カレンダーの予定」を区分けして出す＋そこから報告（権限で出し分け）
- 新しい権限 feature_key `shift_report_calendar`（「勤務変更：カレンダーの予定を履歴で見る・表で見る」・最初はマネージャー・社長・管理者だけ ON）。
  🚨 今の shift_report_todo（報告タブの一覧）と重なる。まとめるか分けるかはレビューで決める（案：shift_report_todo を広げて使い、新しい権限は作らない）
- 履歴の上に区分けのボタン：［すべて］［勤務変更の報告］［カレンダーの予定］［報告がまだの予定］
- 「カレンダーの予定」のカード：「上長が入れた予定（◯◯さんが入力）」・日付・種類・時刻・場所・メモ／状態の札：［報告済み］（同じ勤務日の報告があれば、その報告の状態も）［まだ報告していません］［報告の期限を過ぎました（締め後）］
  ・［この予定で報告する］：今の pickTodo と同じ入れ方で「報告」タブのフォームを開く（判定は buildTodo を1か所に・同じ規則を2か所に書かない）
- 承認者（マネージャー以上）は対象のスタッフを選んで見られる（今の ShiftReportTodo と同じ）。🚨 マネージャー本人には勤務変更の報告が無いので、試すときはパートの方を選んで見る
- 報告とのつながりは今までどおり applicant_id＋work_date（DB の列は足さない）

### 段2：［カード｜表］（同じ権限で出し分け）
- 残業の部品を共用のファイルに出す（components/historyTable/ など）：useOtTableMode→useHistoryTableMode、OtViewSwitch、fillAllDays、OtBackToTable、OtDayWrap。
  OtHistoryTable は「行の中身・状態の字」を呼ぶ側から渡す形にして、残業と勤務変更の両方が使う。🚨 残業の画面の見た目・動きは変えない（試しで残業の表が前と同じことを確かめる）
- 勤務変更の表：［申請｜全日］。全日は給与期間の毎日を1日1行（登録シフト・会社の予定・休暇・カレンダーの予定・勤務変更の報告）。状態の字は勤務変更用（済＝受理・待＝確認待ち・戻＝差し戻し・消＝取消・予＝カレンダーの予定だけで報告まだ）
- 端末に覚える鍵は残業と別（fivem_sr_view_own）

### 段3（将来・今回は作らない）：事前申請 → 受理 → 実績報告
- shift_reports に残業と同じ段（requested／request_confirmed／reported）を足す。今回の作りは状態の字・区分けのボタンを「段が増えても足すだけ」にしておく
- 事前申請ができたら、上長が勤怠カレンダーに入れる予定と二重にならない決まりが要る（正社員の勤怠カレンダーの案内 (334) と同じ考え）

## 出し方
- 段0（画面だけ）→ 段1・段2（画面＋feature_permissions の行1つ・権限でマネージャー以上だけ）→ マネージャーの方に試してもらう → 管理画面の「役職・機能権限」でパートを ON
- DB：feature_permissions の行（新しい権限を作る場合）だけ。表・RLS は変えない
- 社内FAQ：パートに公開するときに足す

## レビューで決まったこと・直したこと（2026-11-05・UI/UX とシニアエンジニアの2体・事実は本番で裏取り）
- 🚨 前提の誤り：shift_report_todo は本番でパート・フロア責任者・リーダー・マネージャー・社長・管理者が ON（一般だけ OFF）＝報告タブの一覧はもうパートに公開済み
  → 新しい権限 shift_report_calendar を作る（履歴の区分け＋表だけ・最初はマネージャー・社長・管理者）。報告タブの一覧は今までどおり shift_report_todo
- 🐛 今ある不具合：フロア責任者は人を選べる（canPickOthers=isApprover）が、他人の勤怠カレンダーを読む権限（attendance_input）が無く、選ぶと黙って「ありません」と出る。
  → 人を選べる条件を「attendance_input か管理者」にそろえる（段1 で一緒に直す）
- 判定は lib/shiftReportTodo に classifyEntry（1件ずつ 'hidden'・'future'・'closed'・'reported'（報告の状態つき）・'todo' を返す）。buildTodo はこれの 'todo' を日で1つにまとめる形に作り直す。ShiftReportTodo と履歴の両方が使う
- 日付ごとに1枚（予定と報告が同じ日なら1枚にまとめ、報告のカードの下に灰色「上長が入れたカレンダーの予定：遅刻 10:00〜」）。予定ごとには出す（同じ日に2つあり得る）
- 札：報告あり（種類が合っているかは判定しない＝time_change などで合わせられないため）／まだ報告していません／報告は当日から（灰色）／報告は取り消し済み（出し直しは管理者へ）／締め後（灰色＋「担当のリーダー・マネージャーにお知らせください」・赤にしない）
- ボタンは［内容を確認 ›］（今の一覧と同じ言葉・押しても送らない）。区分けのボタン［すべて｜報告｜カレンダー｜未報告］は1人分を見ているときだけ
- 状態の字：カレンダーの予定だけの日は「未」（「予」は残業で事前申請 受理済み＝段3 で勤務変更にも使うのでとっておく）。言葉は「予定」単独で使わず「カレンダーの予定」
- 表：時間数の列は通常シフトとの差（summarizeShiftDiffs と同じ）。部品の切り出しは「動きを変えない移動だけ」のコミットを先に出し、残業の表を前後でなぞって確かめる（URL の otday・id の ot-row- は引数で既定を今の値に）
- 試し方：マネージャーは自分の報告が無い→履歴にも人を選ぶ欄。選んで送ると本物の代理報告になる（上に「◯◯さんの画面を見ています（送ると代理報告）」の帯）
- 読めなかったときは「ありません」と出さない（LoadFailedNotice）。オフラインの控えは段1 では作らない
- 未決（ユーザーに聞く）：上長のメモ（notes）を本人に見せるか／先の日のカレンダーの予定も出すか／段0 でオレンジを開いている間の見せ方
