# 開発ルール（社内サイト fivem-portal）

新しく開発に加わる方は、コードを触る前にこのページを読んでください。

---

## はじめに：このシステムの特徴

このシステムには **練習用の環境がありません**。

| | 状態 |
|---|---|
| データベース | 本番が1つだけ（テスト用の別DBはありません） |
| 通知（ベル・メール・スマホ通知・Slack） | 本番のスタッフ46人に届きます |
| Googleカレンダー | 本番の共有カレンダーに書き込まれます ※テスト用に切り替えるスイッチが管理画面にあります |
| 画面 | `master` に push した瞬間、本番サイトが自動で更新されます |
| ソースコード | **GitHub で世界に公開されています（Public）** ※下記参照 |

自分のPCの中だけで試せるのは **画面の見た目だけ** です。それ以外はすべて本番に影響します。

このシステムは46人のスタッフが毎日使う、**勤怠と給与に関わるシステム**です。
「速く作る」より **「壊さない・嘘をつかない」** を優先してください。

---

## 🚨 このリポジトリは「公開」されています

`fivem-inc/fivem-portal` は **Public**（公開）です。
GitHubにログインしていない人でも、URLを開けばコードもファイルも全部読めます。

**これは事故ではなく、意図してそうしています。**
過去に本当の漏洩事故（開発ツールの認証情報が約1年間公開されていた）を起こしたあと、
履歴を消して自動チェックを入れたうえで、判断してPublicに戻しました。
「危険なのはコードが見えることではなく、秘密情報が漏れること」という方針です。
加えて、無料プランではPrivateにすると本番サイトの自動更新が止まる、という事情もあります。

### 守ってほしいのは、この1点だけです

> **`client/.env` と `client/.env.production` に、秘密の鍵を1行でも足さないこと。**

この2つのファイルはGitHubに入っていて、**誰でも中身を読める状態**です。
いま入っているのは、公開しても問題のない3つだけです。

| 入っているもの | なぜ公開してよいか |
|---|---|
| `VITE_SUPABASE_URL` | 接続先の住所。もともと全員のブラウザに配られる |
| `VITE_SUPABASE_ANON_KEY` | 公開前提の鍵。データはDB側のRLS（「この人はこの行しか見られない」をDBが強制する仕組み）で守っている |
| `VITE_VAPID_PUBLIC_KEY` | スマホ通知の「公開」鍵。配るためのもの |

`VITE_` で始まる名前の変数は、**ビルドすると画面のJSファイルにそのまま埋め込まれます**。
つまり `VITE_` を付けた時点で、その値は全利用者のブラウザに配られる＝公開情報です。

### 絶対に書いてはいけないもの（1行足した瞬間に世界公開されます）

- `SUPABASE_SERVICE_ROLE_KEY`（DBの全権限。RLSを無視して全データを読み書きできる）
- `VAPID_PRIVATE_KEY`（スマホ通知の秘密鍵）
- データベースのパスワード
- Slack の Webhook URL
- メール送信（Resend）の APIキー

これらは **Supabase の Secrets**（サーバー側の処理で使うもの）か、
**Vercel の環境変数**（ビルドで使うもの）に入れてください。

### ⚠️ 自動チェックが守ってくれる範囲・くれない範囲

「うっかり鍵をコミットしたら止める」自動チェック（pre-commitフック）がありますが、
守ってくれるのは片方だけです。

| ファイル | 自動チェック |
|---|---|
| `client/.env` | ✅ **止まる**（新規でも追記でも、コミットしようとすると中止される） |
| `client/.env.production` | ✅ **危ない値を書いたときだけ止まる**（ふつうの更新は通る） |

`.env.production` は本番ビルドに必要でGitHubに置く前提のファイルです。
`VITE_` で始まる変数を足すなど、**正当な更新が定期的にあります**。
そのためファイル名では止めず、**追加した行の中身**を見て判定しています。

止まるのは、次の言葉が入った行を足したときです。
　`SERVICE_ROLE` / `VAPID_PRIVATE` / `_PRIVATE_KEY` / `hooks.slack.com` /
　`RESEND` / `PASSWORD` / `SECRET`

🚨 **ファイル名で一律に止めていない理由**（2026-09-01・両担当で合意）
ファイル名で止めると、正当な更新のたびに `git commit --no-verify` が必要になります。
ところが `--no-verify` は **そのコミットのチェックを丸ごと無効にします**。
同じコミットに `.env` や `.pem` が混ざっていても素通りしてしまうので、
「止める」設定にすると、かえって守りが薄くなります。

なお `.env` 側も、`git commit --no-verify` を付ければ強制的に通せます。
自動チェックは「うっかり」を防ぐもので、意図的な操作は止められません。
また、**ここに挙げた言葉以外の秘密情報は止まりません。**
チェックは補助であって、最後は人が気をつける必要があります。

### 🚨 この自動チェックは「PCごと」に入れるものです

このチェックはリポジトリではなく **PCの設定**（Gitのグローバル設定）として入っています。
**新しいPCで開発を始めるときは、そのPCには入っていません。**
設定していないPCでは `.env` も含めて何も止まらないので、下の手順で必ず入れてください。

🚨 **このプロジェクトは `.git/hooks/` を使っていません。**
`core.hooksPath` が指す先を見ます。`.git/hooks/` を見て「無い」と判断すると誤ります
（2026-09-01 に実際に一度間違えています）。

### 新しいPCでの設定のしかた

Git Bash で実行します（PowerShell ではありません）。`<ユーザー名>` は自分のものに置き換えます。

**① 置き場所をつくる**

```bash
mkdir -p "/c/Users/<ユーザー名>/.git-hooks"
```

**② 下のスクリプトを `C:\Users\<ユーザー名>\.git-hooks\pre-commit` として保存する**

🚨 拡張子は付けません（`pre-commit.txt` では動きません）。
🚨 改行コードは **LF** で保存します（CRLF だと `#!/bin/sh` が読めず動きません）。

```sh
#!/bin/sh
# 全リポジトリ共通のpre-commitフック：秘密情報っぽいファイルの誤コミットを防ぐ

# ① ファイル名で止めるもの（そもそもGitHubに置かないファイル）
PATTERN='(^|/)\.claude(/|\.json|\.json\.backup)?$|(^|/)\.vercel(/|$)|com\.vercel\.cli|(^|/)\.env($|\.local$)|\.pem$|\.key$|id_rsa$|(^|/)\.aws/|(^|/)\.ssh/|credentials?\.json$'

MATCHES=$(git diff --cached --name-only | grep -E "$PATTERN")

if [ -n "$MATCHES" ]; then
  echo ""
  echo "コミットを中止しました。秘密情報の可能性があるファイルが含まれています:"
  echo "$MATCHES" | sed 's/^/  - /'
  echo ""
  echo "本当に問題ないファイルの場合は、git commit --no-verify で強制コミットできます。"
  echo ""
  exit 1
fi

# ② 中身で止めるもの（.env.production）
# このファイルは本番ビルドに必要でGitHubに置く前提なので、ファイル名では止めない。
# 一律に止めると VITE_ の追加など正当な更新のたびに --no-verify が要り、
# --no-verify はそのコミットのフック全体（①の判定も）を無効にしてしまう＝守りが薄くなる。
# そこで「追加された行の中身」だけを見て、公開してはいけない値のときだけ止める。
SECRETS='SERVICE_ROLE|VAPID_PRIVATE|_PRIVATE_KEY|hooks\.slack\.com|RESEND|PASSWORD|SECRET'
LEAK=$(git diff --cached -U0 -- '*.env.production' | grep -E '^\+' | grep -Ei "$SECRETS")

if [ -n "$LEAK" ]; then
  echo ""
  echo "コミットを中止しました。.env.production に公開できない値が含まれています:"
  echo "$LEAK" | sed 's/^+//' | sed 's/=.*/=（値は伏せました）/' | sed 's/^/  - /'
  echo ""
  echo "VITE_ で始まる変数はビルド時に画面のJSへ埋め込まれ、全利用者に配られます。"
  echo "この種の値は Supabase の Secrets か Vercel の環境変数へ入れてください。"
  echo ""
  exit 1
fi

exit 0
```

**③ 実行できるようにして、Gitに場所を教える**

```bash
chmod +x "/c/Users/<ユーザー名>/.git-hooks/pre-commit"
git config --global core.hooksPath "C:/Users/<ユーザー名>/.git-hooks"
```

**④ 入ったか確認する**

```bash
git config core.hooksPath
```

自分のパスが表示されれば設定できています。

### 🚨 設定したら、必ず動作を確認してください

「入れたつもり」がいちばん危険です（守られている前提で作業してしまうため）。
使い捨てのフォルダで、下の5つを試してください。

| 試すこと | 正しい結果 |
|---|---|
| `client/.env.production` に `VITE_` の行だけ足してコミット | 通る |
| そこに `SUPABASE_SERVICE_ROLE_KEY=…` を足してコミット | **止まる** |
| そこに `VAPID_PRIVATE_KEY=…` を足してコミット | **止まる** |
| `client/.env` を作ってコミット | **止まる** |
| 普通のファイル（README.md など）をコミット | 通る |

止まったときに、画面に鍵の値がそのまま出ず
`SUPABASE_SERVICE_ROLE_KEY=（値は伏せました）` と表示されることも確認してください。

🚨 試すときは**本番のリポジトリを使わないでください**。`git init` した空のフォルダで行います。

# 第1部　開発の進め方

## 1. 作り始める前

- いきなり作らない。まず「何をどう作るか」の案を出して、**承認をもらってから**作る
- 画面の文言・配色・新しい機能・設計の判断は、必ず先に案を見せる
- 文面（お知らせ・注意書き・メール文など）は **3案** 出して、違いも説明する
- 配色や見た目は、口で説明せず **見本の画像を作って見せる**
  （ダークモードがあるので、明るい画面と暗い画面の両方を並べて見せる）

### 大きな実装・設計変更のときは、作る前にレビューを通す

AIに依頼するときは、そのまま次の文を貼ってください。

```
このプラン内容を、プロのUI/UXデザイナーと、シニアエンジニアの
サブエージェント2体にレビューさせてください。
※他のエージェントへの委任は禁止。あなた自身が直接レビューを実施すること。
```

- **「委任は禁止・自分で実施」を必ず書く**
  （書かないと、丸投げして何も作らずに「完了しました」と返ってくる事故があります）
- レビューは **作ったあとではなく、作る前** に回す
  （実装前に回したおかげで「マネージャーの残業が1件も通知されない」など、
  作ってから気づくと手戻りが大きい穴を先に潰せた実績があります）
- レビューの指摘をそのまま信じない。大事なところは自分で動かして確かめる
  （デザイナーとエンジニアの意見が真っ向から対立したことがあります。
  そのときは8パターン自分で計算して確かめてから決めました）

### 「大きな実装」の目安（1つでも当てはまればレビューを通す）

- お金や勤務時間の計算が変わる（給与・残業・休憩時間）
- 承認や受理の流れが変わる（誰が承認するか、どこまで戻せるか）
- 通知の送り先・タイミングが変わる
- データベースの構造を変える（列を足す・意味を変える）
- 複数の画面にまたがって同じ処理を直す

---

## 2. 作っている間

- **利用者が推測した原因は当てにしない。** 必ず自分で再現して真因を探す
  - 例：「承認前だから操作できない」という報告 → 実際は「当日はボタンが出ない」が原因でした
- 入力画面は「空欄から打つ」だけでなく **「すでに値が入っている状態」でも試す**
  - 実際の運用では値が入っています。空欄だけのテストでは不具合に気づけません
- 画面に「〜できます」と書いたら、**その操作が本当にできるか画面で確かめる**
  - 説明だけあってボタンが無い、という状態を作らない
- **同じ意味のルールを2か所に書かない。** 1か所にまとめる
  - 片方だけ直して食い違う事故が何度も起きています
- **機能を変えたら、FAQ と 画面の注意書きも同時に直す**
  - 片方だけだと、画面が嘘をつくことになります

---

## 3. 本番に出す前（デプロイ）★いちばん大事

- 🚨 **本番に出すときは、必ず確認を取ってから。勝手に出さない**
- 許可は **1回分**。次の変更を出すときは、また確認を取る
- **出す順番を必ず守る**

  ```
  ① データベースの変更 → ② サーバー側の処理 → ③ 画面
  ```

  順番を逆にすると、古い画面が新しい前提で動いて本番データが壊れます
- データベースを変更するときは、本番の前に **「試して、取り消す」で1回通してから**
- 出したあと、**本当に反映されたかを自分で確認する**
  （「送ったつもり」で送れていないことが実際にありました）

---

## 4. 本番に出したあと

- 画面での確認（実機確認）は、必ず担当者にお願いする
- **「選択肢が出るか」で確認を止めない。実際に送信できるところまで確認する**
  - 選べるのに送信するとエラー、という状態が実際にありました
- スマホ（iPhone・Android）と、明るい画面・暗い画面の両方で見てもらう
- 不具合が出たら、直すだけでなく **「なぜ気づけなかったか」も記録に残す**

---

## 5. 記録・引き継ぎ

- 作業が終わったら、リポジトリの `CLAUDE.md` の**先頭**に
  「何をしたか・次に何をするか・気をつけること」を書いて残す
- **次の人はそこしか読まない前提**で書く
- **判断の理由も書く**（何を採用したかより、なぜ他の案を採らなかったかが大事）
- 失敗したことも隠さず書く。同じ失敗を次の人が繰り返さないため

---

## 6. やってはいけないこと

- 確認を取らずに本番へ出す
- **パスワード・鍵・Webhook の URL を チャット・コード・メモに書く**
  - 公開されると誰でも社内データを触れます。実際に約1年間 公開されていた事故があります
  - **`client/.env` / `client/.env.production` への追記も同じです。**
    このリポジトリは Public なので、書いた瞬間に世界に公開されます
    （冒頭の「🚨 このリポジトリは『公開』されています」を必ず読んでください）
- 実際に動かさずに「直りました」と報告する
- 利用者に「動作を確認してください」とだけ言って、確認内容を書かない

---

## 7. 分からないことがあったとき

- 専門用語は、新卒社会人でも分かる言葉にかみ砕いて説明する／してもらう
- 過去にどう判断したかは `CLAUDE.md` に全部書いてあります。まずそこを読む
- **迷ったら「止まって聞く」。勝手に決めて進めない**

# 第2部　2人以上で同時に開発するとき

## 1. いちばん危ない3つ

### ① データベースの変更を、同じ時間に2人でやらない

2人が同時にDBを変えると、後から流したほうが先の変更を壊します。
作業前に一声かけてください。

### ② サーバー側の処理（Edge Function）を出す前に、必ず `git pull` する

これは **上書き** なので、古い状態のまま出すと **相手が直した内容が消えます**。
**エラーも出ないので、消えたことに誰も気づけません。** いちばん怖い事故です。

### ③ `master` に push ＝ 即 本番公開

- 動かない状態・途中の状態では絶対に push しない
- push する前に、必ず担当者に確認を取る（許可は1回分）

---

## 2. 触ってよい範囲の線引き

新しい機能を追加する場合の目安です。

| 触ってよい | 触ってはいけない（要相談） |
|---|---|
| 自分の機能用の **新しい** テーブル（接頭辞をつける） | 既存のテーブル（**列を1つ足すだけでも**） |
| 自分の機能用の **新しい** 関数・RPC | 既存の関数・トリガー・RLSポリシー |
| 自分の機能用の **新しい** Edge Function | 既存の Edge Function（上書きで消えます） |
| | cron（自動実行）・Vault・Secrets |
| | 既存の通知の仕組み |

既存のものは、勤怠・給与・通知に直結していて、
**1か所変えると全社の申請が止まることがあります。**

### 新しいテーブルを作るときの必須事項

- **必ず RLS（行レベルセキュリティ）を有効にする**
  RLSが無いと、ログインした人全員が全データを見られる状態になります
- 管理者かどうかの判定は、必ずこの書き方で

  ```sql
  (auth.jwt() -> 'app_metadata' ->> 'role') = 'admin'
  ```

  🚨 `(auth.jwt() ->> 'role') = 'admin'` は **常に false** になります。
  過去に2回これで全員が保存できなくなりました。

### 通知を足すとき

既存の通知の仕組みには手を入れないでください。
新しい通知の種類を足すと **「設定が無い＝全員に送る」** という作りのため、
スタッフ46人にいきなり通知が飛びます。必要になったら事前に相談してください。

---

## 3. 作業を始める前に宣言する

- 「今日は残業ページを触ります」のように、**触る場所を先に伝える**
- **同じファイルを2人で同時に触らない**（後から直したほうが、相手の修正を潰します）
- 特に大きいファイルは要注意（1つのファイルに数千行あるものがあります）
  - 残業ページ／連絡板／管理画面／休暇申請 は特に競合しやすい
- `App.tsx`（ナビとページの登録）は、新しいページを作るならほぼ必ず触ります。
  触る前に一声かけてください

---

## 4. 作業のたびに（毎回）

| タイミング | やること |
|---|---|
| 始める前 | `git pull`（最新にしてから作業を始める） |
| 出す前 | `git pull`（もう一度。作業中に相手が出しているかもしれない） |
| 出した後 | 本当に届いたか、本番の画面で確認する |

---

## 5. データベースの変更ファイル（マイグレーション）

- ファイル名は **「日付＋番号」で流す順番を表しています**
- 2人が同じ日に作ると同じ番号になり、どちらを先に流したか分からなくなります
  （2026-08-31 に実際に起きました。同じ `20260831200000` を2人が使いました）
  → **番号は自分で決めず、「作った時刻」をそのまま使ってください**

  ```bash
  date +%Y%m%d%H%M%S    # 例: 20260831213045 ← これをファイル名の番号にする
  ```

  秒まで入るので、2人が同時に作らないかぎりぶつかりません
- 🚨 **ファイルを作った＝本番に反映された、ではありません。** 実際に流したか必ず確認する
  （作っただけで放置され、動かないまま気づかなかったことが何度もあります）
- 実行したら「流しました」と報告する
- 🚨 **`supabase db push` は使わない**
  過去の履歴と同期していないため、既存のSQLを全部流し直そうとして失敗します。
  Supabase の SQL Editor に貼って実行してください
- 🚨 **Supabase の画面（Table Editor）から直接 列を足す等はしない**
  変更の記録が残らず、後から誰も追えなくなります。必ずSQLファイルで残してください

---

## 6. テストで本番のスタッフに迷惑をかけない

- 通知のテストは **宛先を自分だけ** にする
- カレンダーのテストは、管理画面で **「テスト用カレンダー」に切り替えてから**
  （終わったら本番に戻すのを忘れずに）
- テストで作ったデータ（申請・お知らせ・欠勤など）は **その日のうちに消す**
- 新しい機能は **いきなり全員に公開しない**
  管理画面に「公開範囲」の設定があります。

# 付録：よく使うコマンド

```bash
# 作業を始める前
git pull
git status

# コードを直したあと（必ず client フォルダで実行する）
cd client
npx tsc -b
npx vite build
npm run lint
```

`npm run lint` で見るのは **`react-hooks/rules-of-hooks` だけ。ここは常に0件**を保ってください。
（他の指摘は既存の積み残しです。増やさなければ大丈夫です）

これを無視すると **「画面が真っ白になる」不具合**を作り込みます。
実際に休暇申請の画面が2週間ずっと壊れていたことがあります。

```bash
# サーバー側の処理を出す（出す前に必ず git pull）
npx supabase functions deploy <関数名> --project-ref xaeynaxctiiyqxjyuzfi

# push したあと、本当に送れたか確認する
git ls-remote origin master
```
