## 2. 2体の意見がそろったこと

- **申請は黙って自動で送らない。**「送れていない申請が1件あります［送る］」を出し、電波が戻ったら知らせるだけ。押すのは本人
  （理由：iPhone は閉じると送れない＝「自動で送られた」と思い込む／締め切り・申請先の休職・重なりで断られたことが伝わらない／上長へのお知らせは端末から送っている）
- そのかわり**二重送信を止める**：端末で作った番号を申請の id にして送る。送り直す前に「もう届いているか」を確かめ、届いていれば緑で「さきほどの申請は届いていました」
- **登録が通った時点で「送信しました」**。お知らせ・メールの失敗は申請の失敗にしない
- 知らせ方：黄色い細い帯（つながっていないとき）＋失敗したときの黄色いカード（何が起きた→消えていない→次にすること）。緑の「接続しました」は出さない（緑は成功だけ）
- 一覧の控えは「自分の申請の履歴」だけ・時刻つき・操作ボタンは押せない。上長の受理待ちなど他人の情報は控えない
- 画面のファイルを端末に保存（Service Worker）は**最後に・範囲を絞って**。トップページは「まず通信・だめなら保存」、部品は版の印つきで直近2版。プッシュ通知と同じファイルなので、止める版（キルスイッチ）を先に用意

## 4. 段3の設計（2026-10-21・レビュー前の案）

### 調べたこと（本番の DB）
- 7つの表（expenses・leave_requests・overtime_reports・overtime_report_segments・shift_reports・business_trip_reports・attendance_exceptions）とも id は uuid・既定値あり。id を指定して入れることを止める決まり（RLS・制約）は無い
- **二重にならない表**：overtime_reports（uq_overtime_manual_per_day＝同じ人・同じ日の手入力は1件）・shift_reports（applicant_id, work_date）・overtime_report_segments（report_id, phase, seg_no）・attendance_exceptions（user_id, date, type）。
  押し直すと 23505 で止まる（2件にはならないが、本当は届いていたのにエラーに見える）
- **二重になりうる表**：expenses（一度に何行も入れる）・leave_requests・business_trip_reports

### やり方（案）
1. 送るたびに端末で番号（uuid）を作り、申請の id にして入れる（lib/safetyStorage の newClientKey と同じ作り方を共通にする）
2. 番号は「同じ中身を送り直す間」だけ使い回す（中身が変わったら新しい番号・成功したら捨てる）
3. 失敗したとき（通信のせい・時間切れ・23505）は、その番号の行がもう有るかを確かめる（select id where id = 番号）
   - 有る → 届いていた。成功として続きの処理（上長へのお知らせなど）を行う。押し直しのときは緑で「さきほどの申請は届いていました」（文は要確認）
   - 無い → 今までどおりの失敗の文（番号は残す＝次に押したときも同じ番号）
   - 確かめも通信で失敗 → 「届いたか分からない」の文（SEND_UNSTABLE_TEXT）
4. 送信の待ち時間に上限（案：20秒）。supabase の abortSignal で打ち切る。打ち切ったら 3 と同じ扱い（届いていても、次に押したとき 3 で分かる＝2件にならない）
5. 交通費は何行も一度に入れる（1回の insert＝全部入るか全部入らない）ので、1行目の番号で確かめる
6. 残業は「申請 → 時間帯の行」の2回。申請が届いていて時間帯で止まった場合も、押し直すと申請は「届いていた」、時間帯は 23505＝届いていた、で続きから進める

### 確かめること
- id を指定した insert が RLS・トリガーで断られないか（本番で begin/rollback）
- 上長へのお知らせを端末から送っている所は、「届いていた」と分かったときに1回だけ送る（最初の送信で応答が落ちたなら、お知らせはまだ送っていない）

### レビュー（2体）と決まったこと・作ったもの（2026-10-21・段3 ✅）
- 🚨 確かめは「失敗のあと」ではなく「押し直す前」：届いていた申請を押し直すと BEFORE トリガー（締め後・重なり・区切り）が 23505 より先に断るため。番号の状態は端末（localStorage `fivem_submit_once:<人>:<種類>`・7日で忘れる）
- 「無い」は決め手にしない（打ち切ったあともサーバーは処理を続ける）。打ち切りは 1.5 秒待って確かめ、まだ無ければもう1回。それでも無ければ「分からない」のまま番号を残す
- 番号の使い回しは「中身が同じ間」。中身は入力から作る（送るたびに変わる時刻 ◯◯_at・confirmed_at は入れない）
- 中身を直して送り直したとき：先にさきほどの番号を確かめ、届いていれば直した内容は送らない（黄色・ユーザー確定）
- 押し直しで届いていたと分かったときは、上長へのお知らせなど後処理をその時点で1回行う（最初の送信では後処理はまだ動いていない）
- 待ち時間：登録の部分だけ 20 秒。8 秒で灰色「通信に時間がかかっています。画面を閉じずにお待ちください。」（ユーザー確定）。fetch の前の合言葉の取り直しには abortSignal が効かないので、待ち自体も打ち切る（raceTimeout）
- 文（ユーザー確定 案A）：lib/netFailure の sendUnstableOnceText(ボタン名)・SEND_DELIVERED_TEXT／SUB・SEND_DELIVERED_CHANGED_TEXT・SEND_SLOW_TEXT。🚨「2件届くことはありません」と言えるのは submitOnce を通した送信だけ（SEND_UNSTABLE_TEXT は残す）
- 部品 lib/submitOnce.ts（submitOnce・newSubmitId＝getRandomValues も使う）。つないだ所：交通費（1回の申請＝1行）・休暇・出張報告・勤務変更（新規・slot は 人:日付）・残業（lib/overtimeSubmitApi の saveOvertimeReport＝1件フォーム・表入力・まとめて申請の3つ。時間帯にも20秒・押し直しで時間帯の 23505 は件数で確かめる）
- 交通費・休暇：登録が通ったらすぐ「登録しました／申請しました」、Slack・お知らせ・メール（休暇は元の申請の取り消しも）は裏で
- 勤務変更の再提出：修正の記録を書き換えのあとへ（押し直すたびに記録が増えていた）
- 検算（作り物の通信・16場面）すべて想定どおり。本番：番号を指定した交通費・出張報告が一般の社員で入る・同じ番号の2回目は 23505（取り消し済み）
- ✅ 段3b（2026-10-21）：残業の実績報告・再提出の押し直し（読み直して同じなら届いていた）／まとめて申請・表入力で通信の失敗が2回続いたら残りを止める（文はユーザー確定）
- 🚧 残り：勤務変更を代わりに出した人（受理の役職でない）は自分の番号を探せない（今までどおりの文になる・2件にはならない）

## 6. 段5 の設計（2026-10-21・レビュー前の案）
圏外でも、一度開いたことがある端末ならアプリが開けるようにする。public/sw.js（通知の仕組み・2人共通）に fetch の処理を足す。

### 決まりの案
- **止める版（キルスイッチ）を先に作る**：sw.js の先頭に `OFFLINE_SHELL = true` を置き、false にして push すると
  ①fetch を横取りしない ②activate のときに画面の保存（shell・assets）を消す。通知・アイコンの保存は今までどおり。
  sw.js は毎回サイトに確かめる配り方（Vercel の既定 max-age=0）なので、push のあと次に開いたときに切り替わる（skipWaiting・clients.claim 済み）
- **横取りする範囲を絞る**（それ以外は今までどおり素通し）
  - 同じサイトの GET のページ移動（mode: navigate）だけ：**まず通信**。通ったら index.html の写しを保存して返す。
    通らない（圏外・5秒の時間切れ）ときだけ、保存した index.html を返す。保存が無ければ今までどおりエラー
  - /assets/ の中身（名前に版の印がある・中身は変わらない）：**保存があれば保存から**、無ければ通信して保存
  - 横取りしない：Supabase（別のサイト）・version.json・sw.js・manifest・faq-widget・POST など
- **古い版の片付け**：assets の保存は件数で上限（例 400件・およそ直近2〜3版）。超えたら古く入れたものから消す
- 新しい版を出したあとも、通信できれば index.html は最新が返る＝今までどおり。圏外のときだけ前の版で開き、つながったら「新しいバージョン」の案内（今の仕組み）で入れ替わる
- 文言の追加なし（段0 の圏外の案内・段4 の黄色い帯はそのまま）

### 確かめたいこと
- 圏外で開く（ログイン済み・一度開いた端末）→ ホームが出る・安否のページが開く
- 新しい版を出したあと：通信ありで開く→新しい版。圏外で開く→前の版→つながると案内
- OFFLINE_SHELL=false にした版で、横取りが止まり、保存が消えること
- 通知（push・押したとき）とアイコンが今までどおり

### 段5 で作ったもの（2026-10-21・別の2体（安全・個人情報／実機の動き）で再確認して直した）
- sw.js：ページを開くときはまず通信。圏外・6秒の時間切れ・サイトの不調（5xx）のときだけ写し（index.html）で開く。届いた HTML はすぐ渡し、写しの保存は裏で
- 🚨 写しを新しくするときは、その HTML が読む部品を先に全部保存してから置き換える（写しだけ新しいと、圏外で開いたとき真っ白になる）
- 部品（/assets/）は保存から。拡張子ごとに許す種類を決め、本物だけ保存（Vercel は無いファイルに index.html を 200 で返す）
- 片付け：ビルドで sw-assets.json（版と部品の一覧）を書き出し、今の版と1つ前の版に無い部品だけ消す
- 新しい版へ読み込み直すとき（useAppUpdate・chunkReload・［更新する］）は lib/reloadFromNetwork（?_net=1）。sw.js はこの印があれば時間切れで写しに逃げず通信を待つ。印は main.tsx で起動時に消す
- 版の確認のときに sw.js の更新も確かめる（registration.update）。sw.js の先頭に SW_VERSION（直したら変える）
- 読めなかったときに「ありません」と出さない：ホーム（通信の失敗のときだけ）・連絡板の受信・グループ／DM・勤務変更の履歴（4つの読み込みを別々に）・確認待ち

### 止める版（キルスイッチ）の手順
1. client/public/sw.js の `const OFFLINE_SHELL = true;` を false にし、SW_VERSION を変えて push
2. 次に通信して開いた端末から、fetch を横取りしなくなり、画面の保存（fivem-shell-v1・fivem-assets-v1）が消える。通知・アイコンの保存はそのまま
3. 🚨 圏外の端末には届かない（次に通信がつながったときから効く）
4. 最後の手段（本当の非常時だけ）：vercel.json で version.json などに `Clear-Site-Data: "storage"` を付ける。sw.js も保存も消えるが、全員ログアウトし、安否確認の未送信も消える

### 知っておくこと
- 段1（端末のログインで画面を出す）と合わせて、強制ログアウト・退職の停止は「圏外の間は」効かない。ただし DB からは何も読めないので、見えるのは端末に残った写し（名前・権限・下書き）だけ。自動ログアウトは端末の時刻で判定するので圏外でも効く
- 保存するのは公開のファイル（index.html・部品）だけ。ログイン後のデータ（Supabase）は保存しない。ログアウトしても消す必要はない
- CSP を付けるなら meta タグで（HTTP ヘッダーだと、写しは古いヘッダーのまま）
- 最初に新しい sw.js が入った起動では、それより前に読んだ部品は保存されない（2回目に開いたときから）
