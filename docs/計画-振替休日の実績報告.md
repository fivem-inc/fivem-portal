# 計画：振替休日にも「実績を報告する」を付ける（2026-10-25）

## きっかけ
- 振替休日は、出した時点で「確認済み」（自己受理）か、上長の受理で「確認済み」になる。実績報告の段階が無い。
- 振替元の日（休日に働いた日）がまだ来ていないうちに出すと、そのとき入れた**予定の時刻**が実際の時刻として確定してしまう。
  当日に時間が延びても、本人は直せない（確認済み・二重計上の見張りで別の申請も出せない）。2026-10-25 の大掃除で実際に起きた。
- 逆の順番（先に休んで、あとで振替元の日に働く）も出せるので、同じことが起きる。

## レビュー（業務・シニアエンジニアの2体・2026-10-26）で決め直したこと
- 🆕 **休む日と振替元の日は同じ給与期間（16日〜翌月15日）のときだけ出せる**（ユーザー提案）。画面と DB の両方で止める。
  これで「締めのあとに報告して支払い済みの期が黙って変わる」が起きない（振替元は遅くとも15日・締めは17日）。過去の振替休日2件はどちらも同じ期間だった（実測）
- 報告できるのは「事前申請 受理済み（request_confirmed）」になってから（受理前の申請中は報告できない）。受理前に報告できると、お知らせ・シフト調整・受理を省く判定が崩れる
- 報告の時刻：［勤務時間が申請と異なりました］は振替元の予定の開始から／［申請どおりに勤務しました］は予定の**終わり**を過ぎてから（開始の時刻に「申請どおり」で確定すると、延びても直せない＝今回と同じ形になる）
- 予定の控え：報告の瞬間（request_confirmed → reported）に、DB のトリガーが変更前の振替元の値を `furikae_planned`（jsonb）へ写す。受理を省く判定と受理ページの「予定」はこれを見る（本人が書ける履歴の控えには頼らない）
- 差し戻し後の再提出は「実績として再提出（reported）」。事前受理の日時（request_confirmed_at）は消さない
- `furikae_report_needed` は新規・再提出のたびに buildOvertimeRecord で計算し直す（JST の今日 ≦ 振替元の日）
- お知らせ「振替休日が受理されました」は、申請中→受理済み（または自己受理で受理済みとして入った）ときだけ。今ある行の移行（確認済み→受理済み）では送らない
- シフト調整：終日の枝を「確認済み・受理済み、または request_confirmed_at があって取消・却下でない」にする（差し戻しで「取り消されました」にならない）
- 変更の有無（changedAxes）に振替元の時刻・休憩・校を足す／報告のときは休む日の通常シフトを取り直さない（editTarget.normal_shift）
- ［内容を修正する］が振替休日の中身を写していない（今もある不具合）→ 直す
- シフト調整の候補（ShiftAdjustTab）：受理済み・報告済みの振替休日の人も「休み」に数える
- 「未報告」の判定を lib に1か所（App.tsx・履歴の件数・ボタン・カレンダーの印）。Edge Function は写し
- 対象外（今回はしない）：打刻の確認（振替元の日は今までどおり「終日」）／管理者の［📋修正］で振替元の時刻を直す（差し戻しで直す）

## ユーザー確定（2026-10-26）
1. **報告のボタンの時刻を分ける**：［勤務時間が申請と異なりました］は振替元の予定の開始から／［申請どおりに勤務しました］は予定の終わりを過ぎてから。翌日以降はどちらもいつでも
   - 例：振替元 10/25 予定 9:30〜18:00 → 9:30〜18:00 は［異なりました］だけ・18:00 以降は両方
2. **同じ給与期間だけ**。止める文は案C（日付を入れる）：
   「休む日（11/2）は 10/16〜11/15 の給与期間、振替元の日（11/17）は 11/16〜12/15 の給与期間です。振替休日は同じ期間の中でだけ出せます。」
3. **報告の画面に［働かなかった］**（振替元の日に体調不良・行事の中止などで働かなかった）。押すと上長に確認が届き、上長が「取り消す（休む日は出勤に戻す）」か「休む日を有休・時間外調整休・欠勤に切り替える」を決める
   - ふつうの順番（働く→休む）：休む日がまだ来ていなければ取り消して出勤／休むなら有休などで出し直す
   - 逆の順番（休む→働く）：休んだ日を有休・時間外調整休・欠勤のどれにするか上長と決める
   - 先に休む（逆の順番）は認める（連勤を避けるため）。社労士に一度確認しておくと安心（ユーザーへ伝えた）
4. **本人が取り消せるのは、休む日・振替元の日のどちらかが来るまで**。来たあとは［働かなかった］か［取消を依頼］で上長へ。休んだ日・働いた日の記録が黙って消えるのを防ぐため（ほかの申請の取消の決まりは今のまま）

## 受理ページ（ユーザー確定 2026-10-26・案A）
- 振替休日の1行は「休日出勤の振替として記録」だけ（今の「（受理で確定します）」は外す。説明は足さない）
- 振替元の日がまだ来ていない振替休日のボタンは、ふつうの事前申請と同じ［事前申請を受理］。新しい行は足さない
- 「2回目の確認があること」は上長にはわかっていることなので画面には書かない（社内FAQ・注意事項で足りる）

## 直す所
### DB（migration 1本）
- 列 `furikae_report_needed boolean not null default false`
- `shift_adjust_recompute` の終日の枝に `'reported'` を足す（足さないと報告した瞬間にシフト調整の相談が「取り消されました」になる）
- `overtime_confirm_as_planned`：振替休日は振替元の列（日・校・開始・終了・休憩・労働）と diff_minutes が直前の控えと同じなら確定
- `notify_overtime_fullday_fyi`：振替休日は request_confirmed になったときに送り、そのあとの confirmed では送らない
- 🚨 本番の実定義から起こす。begin/rollback で なりすまして試す

### Edge Function
- overtime-approve：furikae_report_needed なら受理で request_confirmed（request_confirmed_at）・通知は事前受理の文と event_key／shift_not_needed は事前受理のときだけ
- remind-overtime-unreported：振替休日（furikae_report_needed）は振替元の日で判定

### 画面
- lib/overtimeSubmit：buildOvertimeRecord（状態・request_confirmed_at・shift_adjust_not_needed を報告で上書きしない）／validateOvertime（報告で時刻が変わったら理由が要る）／canReportOvertime（振替元の日で判定）
- lib/overtimeShift：報告できる時刻を振替元の予定から
- lib/overtimeSubmitApi：editLanded で振替元の時刻も比べる
- OvertimePage：報告の画面（予定の表示・［申請どおりに勤務しました］［勤務時間が申請と異なりました］・種別と日付を固定・理由と申請先は読み取り専用・変わった理由）／確認の文／履歴の件数・ボタン／カレンダーの振替元の印から報告／受理ページの表示（予定と実績を並べる）
- App.tsx：実績未報告の数（振替元の日）
- lib/overtimeDayMark・lib/overtimeGrid・lib/overtimeBulkSend・components/ShiftAdjustTab・components/admin/OvertimeAdminTab
- 社内FAQ（振替休日の出し方）と画面の注意事項
