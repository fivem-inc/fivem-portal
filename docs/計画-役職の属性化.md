## 1. 46か所の正体は「概念6つ」

配列の中身で分類すると、判定に使われている概念は6つしかない。

| 概念 | 実際の配列 | 件数 |
|---|---|---|
| **承認者** | `['リーダー','マネージャー','フロア責任者','社長','管理者']` | 5 |
| **マネージャー以上** | `['マネージャー','社長','管理者']` / `['マネージャー','社長']` | 8 |
| **リーダー以上** | `['リーダー','マネージャー','社長','管理者']` / `['リーダー','マネージャー','社長']` | 6 |
| **経営** | `['社長','管理者']` | 4 |
| **序列** | `ROLE_ORDER` / `ROLE_RANK`（並び順・上下判定） | 3＋SQL2 |
| **全役職の一覧** | 選択肢用（プレビュー・FAQ対象・残業設定・ユーザー追加） | 4 |

🚨 **フロア責任者の扱いが概念ごとに違う**（承認者には入る／リーダー以上には入らない・2026-07-19 決定）。
　 既存の `roles.sort_order` は パート1／一般2／リーダー3／マネージャー4／**フロア責任者5**／社長6 で
　 実際の序列と一致していない。**「序列1本」では表せない。役職ごとに明示的なフラグが要る。**

🚨 **「管理者」は2つの概念が混ざっている。**
　 (a) `auth.jwt() app_metadata.role = 'admin'`（`is_admin()`・システム管理者）
　 (b) `profiles.role_title = '管理者'`（役職としての管理者＝経理）
　 Edge Function の create-user 等は (b) を見ている。属性化のとき、どちらの意味かを1つずつ確かめる。

**DB側にはすでに正しい形の入口がある**：`is_admin()` / `is_manager_plus()` / `is_leader()` /
`overtime_role_rank()` / `resolve_role_recipients()`。ただし**中身が名前の列挙**。
→ **中身だけ差し替えれば、それを呼ぶポリシーは1行も触らずに属性ベースになる。**

## 2. 設計方針

> **役職名は「表示」にだけ使う。判定・宛先・データの参照には使わない。**

`roles` に列を足す（すべて `not null`。**nullable にすると `not r.is_x` が NULL で素通りする**＝09-09 の穴と同型）：

| 列 | 型 | 意味 | 初期値（現行の動きを再現） |
|---|---|---|---|
| `acts_as` | text null | **承認フロー上の立場**（`leader` / `manager` / `accounting` / `president`）。**非一意**＝会長も `president` に立てる | リーダー→leader／マネージャー→manager／管理者→accounting／社長→president／他は null |
| `is_approver` | bool | 承認者（休暇・勤務変更の受理・差し戻し） | リーダー・マネージャー・**フロア責任者**・社長・管理者 |
| `is_leader_plus` | bool | リーダー以上（先行公開・回覧・休暇の全件閲覧） | リーダー・マネージャー・社長・管理者（**フロア責任者は含まない**・2026-07-19 決定） |
| `is_manager_plus` | bool | マネージャー以上（安否の発信・自己受理・電話番号の閲覧） | マネージャー・社長・**管理者** |
| `is_board_approver` | bool | 備品購入の**決裁者**（3万円超の全員承認・領収書の閲覧） | マネージャー・社長（**管理者は含まない**） |
| `is_org_wide` | bool | 組織全体を見る立場（通知のグループ絞り込みの対象外・「社長のみ」先行公開） | 社長・管理者 |
| 序列 | — | **§9-Q3 で決める**（`sort_order` を序列として使うか、別列 `rank` を持つか） | 本番の `sort_order` はすでに実序列と一致 |

🚨 **`is_manager_plus` と `is_board_approver` を分けるのが、このv2の要点。**
　 v1 のように1つに寄せると、経理（管理者）が3万円超の決裁に自動で入り、全員承認が経理の票待ちで止まる。

- `acts_as` の役割：通知の宛先キー（`leader` / `manager` / `president`）・「社長を引く」処理・
  承認フローの段の判定（`role_title === 'マネージャー' ? 'manager' : 'leader'` 等）は **`acts_as` で引く**。
  会長を作って `president` に立てれば、**社長宛の通知と最終受理にその日から入る**（§1b の要件）。
- フラグの役割：「〜以上」「承認者」の判定。**新設役職は管理画面のチェックで属性を付けるだけ**。
- 🚨 **「管理者」の2概念を切り離す。** (a) `is_admin()`（app_metadata）はシステム管理者で、役職の属性には**含めない**。
  全能は今までどおり各ヘルパーの `is_admin() or …` で持つ。(b) 役職「管理者」＝経理は、上の表のとおり**役職行として個別に**属性を持つ。
  改名して「経理」にできるようになるのが属性化の効果そのもの。
- `master_options` の役職一覧は**廃止**し、`roles` を唯一の一覧にする（二重管理をやめる）。

**属性の置き場（§9-Q2 で決める）**
- A：`roles` の列（上の表）。意味が素直。UIは「役職の区分」カードを1枚足す
- B：`feature_permissions` の `feature_key`（`attr:manager_plus` 等）。既存の UI・キャッシュ・プレビュー・`has_feature_permission` をそのまま使える。
  🚨 ただし `is_fixed`（管理者）は UI で**常にON**扱いになるため、`is_board_approver` が管理者=true になる＝上の事故と同じ。例外処理が要る

**クライアントの読み方（レビュー採用）**
`useAuth` が **`roles` を7行まるごと1回読み**、`role_id`（無ければ名前）から属性を引く。
これで ①プレビュー役職も同じ経路 ②プレビューの一覧も `roles` から出る（新設役職が自動で並ぶ）
③キャッシュは `perms` と**別キー**に置き、`AUTH_CACHE_VERSION` を上げない（上げると46人全員の初回描画でナビが減る・2026-07-13 の症状）。

🚨 **判定は1か所に集約する。**
- DB … ヘルパー関数（`is_manager_plus()` 等）だけが `roles` を読む。ポリシーはヘルパーを呼ぶ
- クライアント … `useAuth` だけが `roles` を読み、`isApprover / isLeaderPlus / isManagerPlus / isExecutive / roleRank` を返す。画面はそれを読むだけ
- Edge Function … 共通ヘルパー（`_shared/roles.ts`）だけが `roles` を読む

## 6. リスクと、まだ決めていないこと（レビューで見てほしい所）

1. **`code` を持つか、フラグだけで足りるか。** 通知の宛先キー（president）と「社長を引く」処理（`remind-admin-setup` 等）は
   フラグでは表せない（経営＝社長＋管理者なので、社長だけを指せない）。→ `code` が要る、という判断。
2. **`is_executive` に管理者を含めるか。** 現行の `['社長','管理者']` を再現するなら含める。
   ただし (a)(b) の管理者の混在があるので、含めた結果 経理アカウントが「経営」扱いになる。現行どおりだが意図的か。
3. **`profiles.role_id` の同期をトリガーでやるか、書き込み側を全部直すか。** 書き込みは3か所
   （UsersTab の変更／FeaturePermissionsTab の一括変更／create-user）。トリガーなら漏れない。
4. **notification_settings の JSON を `code` に置換する変換**。手で書いた設定が壊れないか。変換前に全行を退避。
5. **段2の実数**は本番の `pg_policies` を読まないと分からない（migration 28本は履歴であって現在形ではない）。
6. **Edge Function 13本の deploy** は「関数を丸ごと置き換える」。相手（場所予約）の変更を巻き込まないよう **deploy 前に必ず git pull**。
7. **時間**。今夜で段0〜3まで（サーバーの判定＋画面）が現実的な上限。4〜7 は日を分ける。
   🚨 段1・2 を夜に流すこと自体のリスク（翌朝 9:10 の毎朝のお知らせ、出勤時のログイン）。
8. **`is_active` の扱い**。既存ヘルパーは `is_active = true` を条件に持つ。属性化しても残す。
9. **CalendarPage の `ROLE_ORDER = ['社長','三役','マネージャー','リーダー']`** … 「三役」はグループ名で役職ではない。
   ここは役職の序列ではなく表示のグルーピング。属性化の対象外として別扱いにする。
10. **キャッシュ**。`useAuth` は権限を端末に保存している（`AUTH_CACHE_VERSION`）。属性を足したら版を上げる。
11. **通知の宛先キーが3つ固定**（`leader` / `manager` / `president`）。会長・副社長を作ったとき
    「社長宛」に含めたければ、宛先を**役職一覧からのチェック**（`roles.id` を保存）か
    **属性宛**（「経営」に届く）に変える必要がある。`code` は「社長そのものを指す」処理
    （`remind-admin-setup` 等）にだけ使い、宛先の既定値は属性で解決する、という切り分けが要る。
12. **`rank` の同点**。社長1／管理者1 のように同点を許すか、会長0 のように上に足せるか。
    序列は「上下の判定」（残業サマリーの閲覧範囲）に使われているので、同点の意味を決めておく。
