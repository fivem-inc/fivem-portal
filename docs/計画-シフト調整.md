# 計画：シフト調整の作業場（2026-09-12 設計確定・未実装）

休暇や欠勤で空いた穴を、誰がどう埋めるかを相談して決める場所を作る。
いまは休暇申請が来ると LINE に書いて相談しており、**話が埋もれる**のが困りごと。

- 決め方：`/grill-me` の一問一答（2026-09-11〜12）→ 専門エージェント4体のレビュー（使う人の動線／作りと安全／UI・UX／シニアエンジニア）→ 反映
- 状態：**設計のみ。コード・DB は1行も変えていない**
- 🚨 この文書の「決まったこと」は**ユーザー確定**。蒸し返さないこと
- 🚨 レビューの指摘は鵜呑みにせず、判断を左右する主張は本番DB・コードを読んで裏取りした（下の「裏取りした事実」）

## 1. きっかけ・対象

- 次の2つで、調整の場を**自動で作る**（いつ・どこ・誰の休みかが入った状態）
  - **休暇**が「受理済みの3つの状態（`manager_approved` / `admin_approved` / `approved`）のどれかに**初めて**入ったとき」
    🚨 「マネージャー受理の時点」では**漏れる**。調整休は `step2_pending` からいきなり `approved` になる
  - **勤怠カレンダーで欠勤（`attendance_exceptions.type = 'absent'`）を登録したとき**
- 🚨 **有給奨励日（`purpose='有給奨励日'`）は対象外**（本人の回答がそのまま受理済みで入り、1日最大20件あるため）
- **日ごとに1つずつ作る**（3日間の休暇なら3つ）。一覧では「◯◯さんの休暇（3日間のうち2日目）」とつながりが分かるように出す
- **過去の日は知らせず、閉じた状態で作る**。決定されないまま日付を過ぎたものは翌朝に自動で閉じる
- **対象者が退職（`profiles.is_active=false`）していたら**、翌朝に「対象者が在籍していません」で自動で閉じる
- 🚨 欠勤を含める理由：**パートの休みはほぼ欠勤で入る**（欠勤：パート34・正社員5〔90日〕／休暇71件中パート1）

## 2. 置き場所と画面

- **勤怠カレンダー（/calendar）の中の「シフト調整」タブ**。ナビにページは増やさない
- 🚨 **いまの勤怠カレンダーにタブは1つも無い**（黄色い説明枠 → 直近6ヶ月サマリー → 月カレンダー（◀▶）→ その月の一覧 の一本道）
  - タブは**黄色い説明枠の直下**に置き、「シフト調整」に切り替えたら**6ヶ月サマリー・◀▶・凡例・月カレンダー・月別リストを丸ごと隠す**
    （隠さないと「9月を見ているのに10月の件が出る」ことになる）
  - 🚨 タブは**共通部品 `client/src/components/PageTabs.tsx`（`variant='boxed'`）を使う**。自作しない（休暇・残業・備品購入・勤務変更の4画面が既に使用）
- 一覧は「未調整・今日以降」を月に関係なく出す。7日以内は橙の文字、それ以降はグレー
- 休みの行の**今の印（シフト 未／調整済／確認済）をそのまま入口**にする。押すとその日の調整の場が開く
  - 🚨 **欠勤の行には今チップが無い**（右端は「取消」ボタンだけ）。**欠勤の行の2行目にも同じ印を足す**
  - 🚨 **未調整の行から1タップで「確認済（変更なし）」にできる道は残す**（ユーザー確定）。
    いまも1タップで済む操作を4手に増やさない。誰かを当てるときだけ調整の場を開く
- 調整の場は全画面。並べ方（スマホ375px前提）：
  1. 見出し（日付・誰の休みか・状態）
  2. **誰がいつ入るか**（午前・午後などの時間帯＋人）← 決めることを最上段
  3. ▶ 候補を見る（勤務している人／休みのパート）… **既定は閉じる**
  4. ▶ 案と確認（案・意見の期限・確認した人）… 既定は閉じる
  5. 相談（コメント。備品購入のコメント欄と同じ見た目）… 既定は開く
  6. 画面下に固定で［決定する］［確認済（変更なし）で閉じる］
- 中身は**別ファイルの部品**。`CalendarPage.tsx`（2,462行・状態60個）にはタブと印の差し替えだけ
- 調整の場は URL に `?adjust=<id>` を持つ。閉じるは**自分で開いたときだけ** `navigate(-1)`、
  通知から直接開いた人には「一覧へ」を出す（FAQで踏んだ罠と同型）
- 🚨 勤怠カレンダーを開けるのは**リーダー・マネージャー・社長・管理者の11人**。
  新しい権限を ON にしても勤怠カレンダーの権限が OFF の役職は入れない → 権限の画面に注意書き

## 4. 候補の出し方

- その日の人を「**勤務している人**」「**休みのパート**」に分けて並べる（週の基本シフト＋欠勤・休日出勤・休暇）
- すでに休み・別の調整に入っている人には印。誰を当てるかは人が決める
- 🚨 **パートの週の基本シフトもマスターに入れる**。取り込む前は「休み」ではなく「**シフト未登録**」と出す
  （いまパート18人は0件。取り込み画面 `OvertimeShiftImport` はパートを除外している）

## 5. パートへの依頼

- **その都度選べる**：直接連絡して結果を記録する／アプリで依頼を送る
- アプリの送り方も選べる：1人ずつ／複数人に送って人が選ぶ／複数人に送って**先に答えた人**を案に入れる
  （どの場合も**決定は⑤の権限の人**が押す）
- 選ばれなかった人への伝え方は**両方作り、送るときに選べる**（管理画面で出す・出さないも切り替え）
  - 既定は「返事の画面に出すだけ」。文面（ユーザー確定）：
    - まだ決まっていない間 …「**現在調整中です**」
    - 決まったあと …「**この日の担当は決定しました。ご返事ありがとうございました。**」
    - 🚨 「埋まりました」は使わない
- 返事の期限は**任意**（日付と時刻）。過ぎたら「返事なし」と出し、送った人に知らせる。パートへの催促はしない
- 🚨 パートは勤怠カレンダーも調整の場も開けない。**返事は専用のページ**（例 `/shift-request?id=`）。
  既存の `/overtime` は `canOvertime` で塞がれており**パートは入れない**。作りは `OvertimeProposalResponse` に倣う
- 🚨 スマホ通知を登録しているパートは**18人中6人**。
  - 送る画面の候補の横に「**スマホ通知なし（アプリを開くまで気づきません）**」と出す
  - パートのホームに「返事がまだ」のバナーを1本出す（既存 `OvertimeApprovalBanner` と同じ形）

## 6. 案と確認

- ③が案を作る。案に「いつまでに意見をください」の期限（日付と時刻）を付けられる
- ②が「確認した」を押せる（誰がいつ）。**押さなくても決定できる**
- 🚨 **急ぐときは案を作らずに直接決定できる**（当日の欠勤4件はすべて朝9時前の登録）
- 意見の期限を過ぎたら「期限切れ（確認 ◯人）」と表示し、**案を作った人に知らせる**

## 7. 決定したとき（⑤の権限）

- 記録：未調整 → 調整済み。代わりに入る人へのお知らせは ON/OFF（休んだ本人には送らない）
- パートは**勤怠の登録**／正社員は**残業申請の依頼**（それぞれ ON/OFF）。切り替え日は管理画面で決める
  - 残業申請を使えない人の行は依頼を押せなくし、理由を出して勤怠の登録を選べるようにする（決定は止めない）
- 人＋時間帯を何組でも（`work_segments`）
- 🚨 **同じ人・同じ日に2つの調整へ当てることがある**（ユーザー確定）。
  勤怠記録は `(user_id, date, type)` で一意なので、**すでにその人のその日の休日出勤があれば時間帯を足す**、
  無ければ新しく作る。`enforce_attendance_exclusive` は INSERT と「種類・人・日付」の変更でしか動かないので、
  時間帯だけを足す更新は通る
- 🚨 弾かれたとき（23514 排他・**23505 重複**・23503 参照）は**1つの例外ブロックで全部取り消し**、決定を止めて理由を出す
- 休日出勤の残業申請は本人が出す

## 8. 決定のあと・休みの取り消し

- **決定を取り消す**（⑤）：決定で入れたものを一覧で出し、1つずつ「取り消す／残す」。黙って消さない
- **元の休みが取り消されたとき**：決定前は自動で閉じる／決定後は表示して①に知らせ、人が判断
- **受理済みの休暇の日付が変わったとき**：決定済みなら閉じず「元の休みが変わりました」と出して人が決める
- 🚨 「取消」以外に**差し戻し・行ごとの削除・`admin_edit_leave_request`・欠勤の「取消してこの内容で入力」**でも動かす

## 9. 調整が要らなかったとき

- 言い方は**今の「確認済（変更なし）」に寄せる**（ユーザー確定。新しい言い方を作らない）
- 未調整の行から**1タップ**で閉じられる（⑤）。調整の場からも閉じられる

## 10. お知らせ

| いつ | 誰に | 設定 |
|---|---|---|
| 調整の場ができたとき | **送らない**（今の受理・勤怠のお知らせ＋カレンダーの印で気づく） | — |
| 休みの3か月前・1か月前（既存 `remind-leave-shift-adjust`） | ①の権限の役職（既定）。管理画面で指定すればそちらが優先 | 既存（時期・時刻・前後の幅） |
| **休みが◯日以内なのに未調整（毎朝のまとめ・新設）** | 同上 | **何日以内（既定7日）／送る時刻（既定9時）／送る曜日／ベルだけにする**を管理画面で |
| 決定・決定の取り消し | 代わりに入る人 | 決定の画面で ON/OFF |
| パートへの依頼・返事の期限切れ・意見の期限切れ | 本人／送った人／案を作った人 | — |
| 決定の連絡（選ばれなかったパートへ） | 選ばれなかったパート | 既定は送らない（返事の画面に出すだけ） |

- 🚨 毎朝のまとめの cron は **`*/15`＋送る時刻の窓**（既存と同じ形）。`0 0 * * *` だと設定の時刻が効かず、落ちた回は飛ぶ
- 🚨 送信済みの印は**表を作らず** `notifications` の `reference_id='shift_adjust_digest:YYYY-MM-DD'` で
  前回ぶんを消して付け直す（`remind-application-request` と同じ形）。表を作らないので掃除も不要
- 🚨 新しいお知らせは `notification_settings` の行と `push-dispatch` の EVENT_MAP を必ず足す
- 休んだ本人には中身もお知らせも出さない

## 11. 記録の掃除

- 相談の記録（コメント・案・確認・依頼と返事）は、調整が終わって**90日で消す**（毎夜の cron）
- 🚨 **見出しの行（状態）は残す**（消すと未調整に戻りお知らせが再び飛ぶ）。`purged_at` を立て、画面に「記録は消えました」と出す
- 容量：DB全体 41MB／年700件程度 → 90日保持で最大5MB程度

## 表の設計（レビューの提案を採用）

- **`shift_adjust_slots`**（見出し・日ごと）
  `target_user_id` / `target_date` / `cause`（`'leave' | 'absent'`）/ `cause_leave_request_id` / `cause_attendance_exception_id`
  （どちらも `on delete set null`）/ `status`（`pending` / `working` / `decided` / `no_change` / `closed_past` / `cause_cancelled`）

## 作り方（レビューの提案を採用）

- **自動で作る仕組みは DB トリガー**（受理は画面の複数経路・奨励日の insert・SECURITY DEFINER の関数を通るため）
  - 休暇：`leave_requests` の INSERT／UPDATE（status・leave_dates・start_date・end_date・user_id）／DELETE
  - 欠勤：`attendance_exceptions` の INSERT／UPDATE（type・date・user_id）／DELETE
  - 両方から「その人・その日はまだ休みか」を数え直す**1つの関数**（何度動いても同じ結果）
  - 🚨 関数は **SECURITY DEFINER**（受理者の許可では新しい表に書けない）。本体を
    `begin … exception when others then raise warning …; end;` で包み、**失敗しても受理を巻き戻さない**
  - 🚨 トリガー名は既存より後ろ（例 `trg_zz_shift_adjust`）。既存の `leave_requests_sync_overtime` を先に終わらせる
  - 🚨 `leave_dates` は **text**。`::jsonb` のキャストが失敗すると文ごと巻き戻るので、必ず例外で受ける
- **状態は `leave_requests.shift_adjust_status` にも書き写す**。
  既存の毎朝のお知らせ（cron `*/15`）と索引 `idx_leave_shift_adjust_pending` がこの列を見ており、
  書き写さないと**テスト中に本物のスタッフへお知らせが飛び続ける**。
  あわせて `set_leave_shift_adjust` を「新しい表も同時に更新する」版に差し替える（🚨 本番の実定義から起こす）
- 相談の記録・依頼は別の表。**子の表にも「休んだ本人でない」を `exists`（親を見る）で掛ける**（親だけだと子を直接読まれる）
- RLS は `(select has_feature_permission('…'))` と括る（行ごとでなく1回の評価で済む）
- **決定の RPC**：⑤を関数の中で確かめる／行を FOR UPDATE で押さえる／勤怠の登録・依頼・状態の更新を1つの例外ブロックに入れる／
  「指定した人が残業申請の権限を持つか」を DB で確かめる関数を新設
- `gcal-sync` は DB から呼べない → 決定の確定後に画面から呼ぶ。🚨 **未反映の印は調整の場の行に持ち**、
  ①の権限の誰でも押し直せるようにする（ブラウザを閉じられても取り返せる）
- 2人共通で触るもの：`useAuth.ts`／`FeaturePermissionsTab.tsx`／`NotificationsTab.tsx`／`App.tsx`／`push-dispatch`。**触る前に相手へ一声**

- `leave_requests` の SELECT は `is_leader_plus()` なら全件 → 調整の中身は別の表にする

- `attendance_exceptions`：`uq_attendance_exceptions_user_date_type (user_id, date, type)`。
  `trg_enforce_attendance_exclusive` は **BEFORE INSERT OR UPDATE OF type, user_id, date**（時間帯だけの更新では動かない）。休日出勤37件
- `weekly_shift_patterns` の SELECT：本人／管理者／`shift_pattern_directory`／`overtime_summary`
- 既存の `remind-leave-shift-adjust`：cron は **`*/15`**、送るのは休みの3か月前・1か月前。設定は `leave_shift_alert_settings`
  （`enabled` / `months_before {3,1}` / `send_time 09:10` / `window_minutes 120`）。印は休暇ごとに2列
- `push-dispatch` は EVENT_MAP に無い種類を送らずに飛ばす（2人共通の関数）
- スマホ通知を登録しているパートは18人中6人。`/overtime` は `canOvertime` で塞がれていてパートは入れない
- 共通のタブ部品は `client/src/components/PageTabs.tsx`（休暇・残業・備品購入・勤務変更の4画面が使用）
- 勤怠カレンダーにタブは無く、欠勤の行にはチップも無い（右端は「取消」だけ）

## この機能で特に効く決まり（CLAUDE.md より）

- 新しい関数は `revoke execute … from anon` を明示し、適用後に実際に呼んで確かめる
- 既存の関数を `create or replace` するときは**本番の実定義から起こす**
- 状態を持つので「**作る→消す→もう一度作る**」まで取り消し版で通してから完了と言う
- 記録を貯める表には**掃除の cron を同時に作る**
- 社内FAQと画面の注意書きも同時に直す／Edge Function を触ったら `npx deno check`

## 呼び名と、依頼に入れる中身（2026-09-12 ユーザー確定）

- パートへ送る依頼の呼び名は「**出勤のお願い**」。🚨 既存の「申請の依頼」（`application_requests`）と紛れないようにするため
  - ベルの文面：「📅 9/18（木）の出勤のお願いが届いています」
  - 返事のボタンは「**入れます／入れません**」
- 依頼に入れるもの：**日付・時間帯・校**（例「9/18（木）9:00〜13:00／四条本校」）
  - 時間帯は調整の場で決めた `segments` をそのまま出す
  - 校は、休暇なら日ごとの勤務校（`leave_requests.leave_locations`）、欠勤なら記録の校（`attendance_exceptions.location`）から出す
  - 🚨 **誰の代わりかは載せない**（休んだ人の名前・休暇の種類は依頼の表に持たない）
