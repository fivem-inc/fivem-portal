# 計画：シフト調整の作業場（2026-09-12 設計確定・未実装）

休暇や欠勤で空いた穴を、誰がどう埋めるかを相談して決める場所を作る。
いまは休暇申請が来ると LINE に書いて相談しており、**話が埋もれる**のが困りごと。

- 決め方：`/grill-me` の一問一答（2026-09-11〜12・申請系セッション）→ 専門エージェント2体のレビュー → 反映
- 状態：**設計のみ。コード・DB は1行も変えていない**
- 🚨 この文書の「決まったこと」は**ユーザー確定**。蒸し返さないこと
- 🚨 レビューの指摘は鵜呑みにせず、判断を左右する主張は本番DB・コードを読んで裏取りした（下の「裏取りした事実」）

---

## 1. きっかけ・対象

- 次の2つで、調整の場を**自動で作る**（いつ・どこ・誰の休みかが入った状態）
  - **休暇**が「受理済みの3つの状態（`manager_approved` / `admin_approved` / `approved`）のどれかに**初めて**入ったとき」
    🚨 「マネージャー受理の時点」では**漏れる**。調整休は `step2_pending` からいきなり `approved` になる
    （`LeaveApprovals.tsx` の handleApprove / handleApproveAsSelf が `isChosei ? 'approved' : 'manager_approved'`）
  - **勤怠カレンダーで欠勤（`attendance_exceptions.type = 'absent'`）を登録したとき**
- 🚨 **有給奨励日（`purpose='有給奨励日'`）は対象外**。本人の回答がそのまま受理済みで入り、1日最大20件あるため、
  作ると一覧とお知らせが埋まる（休暇申請71件のうち50件が奨励日）
- 休暇の種類ではほかに絞らない
- **日ごとに1つずつ作る**（3日間の休暇なら3つ）。一覧では「◯◯さんの休暇（3日間のうち1日目）」とつながりが分かるように出す
- **過去の日は知らせず、閉じた状態で作る**。決定されないまま日付を過ぎたものは翌朝に自動で「過ぎた日」として閉じる
  （どちらも消す時期〔90日〕の対象に入る）
- 🚨 欠勤を含める理由（実測）：**パートの休みはほぼ休暇申請ではなく欠勤で入る**
  （欠勤：パート34件・正社員5件〔直近90日〕／休暇申請：71件中パートは1件）

## 2. 置き場所

- **勤怠カレンダー（/calendar）の中の「シフト調整」タブ**。ナビにページは増やさない
- タブには月に関係なく「未調整・今日以降」の一覧（件数つき）。押すとその日の調整の場が全画面で開く
- 勤怠カレンダーの休みの行にある**今の印（シフト 未／調整済／確認済）の場所をそのまま使う**。
  状態を4つにし（未調整／調整中／調整済／調整不要）、**押すとその日の調整の場が開く**。ボタンは増やさない。
  🚨 一覧はもともと日付ごとの行なので、日ごとの状態がそのまま印になる（複数日の休暇で日ごとに状態が違っても出せる）
- 中身は**別ファイルの部品**に作る。`CalendarPage.tsx`（2,462行・状態60個）にはタブと印の差し替えだけ
- 🚨 勤怠カレンダーを開けるのは**リーダー・マネージャー・社長・管理者の11人**
  （`leave_calendar` 権限＋ルートは App.tsx で `!isAdmin && !canCalendar` をトップへ戻す）。
  新しい権限を ON にしても、勤怠カレンダーの権限が OFF の役職は入れない → 権限の画面に注意書きを出す

## 3. 権限（機能権限を5つ新設・ナビには出さない）

| # | 権限 | 公開後の既定 ON |
|---|---|---|
| ① | 見る・コメント | リーダー・マネージャー・社長 |
| ② | 案の確認（「確認した」ボタン） | リーダー・マネージャー・社長 |
| ③ | 案を作る・意見の期限を付ける | マネージャー・社長 |
| ④ | パートへの依頼（直接連絡の記録・アプリ送信） | マネージャー・社長 |
| ⑤ | 決定・決定を取り消す・調整不要で閉じる | マネージャー・社長 |

- 管理者は常に可
- 🚨 **テスト中は5つとも社長・管理者だけ ON で本番に出す**。テストが済んだら管理画面でリーダー・マネージャーを ON にするだけで公開
- 🚨 **テスト中は今の運用を据え置き、公開日に一度に切り替える**
  - 据え置くもの：カレンダーの今のボタンの動き・`leave_shift_adjust` 権限と `set_leave_shift_adjust`・既存のお知らせの宛先
  - 先に切り替えると、テスト中は社長・管理者しか調整済を記録できず、マネージャーにお知らせも届かなくなる
- 公開日に `leave_shift_adjust`（シフト調整の記録）は**管理画面から消す**。DB の判定（`set_leave_shift_adjust`）も⑤に置き換える

## 4. 候補の出し方

- その日の人を「**勤務している人**」「**休みのパート**」に分けて並べる
  - 材料：週の基本シフト（`weekly_shift_patterns`）＋勤怠カレンダーの欠勤・休日出勤・休暇
  - すでに休み・別の調整に入っている人には印
- 調整の順（運用）：いるスタッフで回せるか → その日に勤務している人で調整 → 休みのパートに依頼
- 誰を当てるかは人が決める（自動で決めない）
- 🚨 **パートの週の基本シフトもマスターに入れる**（ユーザー確定）
  - いまパート18人は0件。取り込み画面（`OvertimeShiftImport`）はパートを明示的に除外している
  - 🚨 **先に `supabase/migrations/20260911160813_fix_sync_overtime_from_leave.sql` を適用すること**
    （マスターを読む唯一のDB関数に列名の不具合があり、時間外調整休の最終受理が失敗する。引き継ぎの (35)）
  - 取り込む前は、候補の一覧で「休み」ではなく「**シフト未登録**」と出す

## 5. パートへの依頼

- **その都度選べる**：直接連絡して結果を記録する／アプリで依頼を送る
- アプリで送るときの送り方も**選べる**：
  - 1人ずつ送って返事を待つ
  - 複数人に送り、返事を見て人が選ぶ
  - 複数人に送り、**先に答えた人**を案に入れる。🚨 この場合も**決定は⑤の権限の人が押す**
- 選ばれなかった人への伝え方は**両方作り、送るときに選べる**（管理画面で出す・出さないも切り替え）
  - **既定は「返事の画面に出すだけ」**。通知は送らない。文面（2026-09-12 ユーザー確定・案A）：
    - まだ決まっていない間 …「**現在調整中です**」
    - 決まったあと …「**この日の担当は決定しました。ご返事ありがとうございました。**」
    - 🚨 「埋まりました」は使わない（断られた感じが出る、とユーザー指摘）
  - もう一方は「決定したときに知らせる」（同じ文面を通知でも使う）
  - 🚨 パートは勤怠カレンダーも調整の場も開けない。**伝わる場所は依頼の返事の画面だけ**
- 返事の期限は**任意**（日付と時刻）。過ぎたら調整の場に「返事なし」と出し、**送った人に知らせる**。パートへの催促は送らない
- 🚨 スマホ通知を登録しているパートは**18人中6人**。送る画面の候補の横に「**スマホ通知なし（アプリを開くまで気づきません）**」と出す

## 6. 案と確認

- ③の権限の人が案を作る。案に「**いつまでに意見をください**」の期限（日付と時刻）を付けられる
- ②の権限の人が「**確認した**」を押せる（誰がいつ確認したかを残す）。**押さなくても決定はできる**
- 🚨 **急ぐときは案を作らずに直接決定できる**（⑤の権限。当日の欠勤4件はすべて朝9時前の登録だった）
- 意見の期限を過ぎたら「期限切れ（確認 ◯人）」と表示し、**案を作った人に知らせる**。見る人への催促はしない

## 7. 決定したとき（⑤の権限）

- 記録：未調整 → 調整済み（常に）
- **代わりに入る人**へのお知らせ：ON/OFF（直接伝えるときは切る）。🚨 休んだ本人には送らない
- パートは**勤怠の登録**／正社員は**残業申請の依頼**（それぞれ ON/OFF）
  - 「いつから正社員を残業申請の依頼にするか」は**管理画面で切り替え日を決める**
    （いまは一般12人・フロア責任者5人が残業申請を使えない。権限を開ける日と同じ日にする運用）
  - 🚨 備え：残業申請を使えない人の行は「残業申請の依頼」を押せなくし、理由を出して勤怠の登録を選べるようにする（決定は止めない）
- 「午前は◯◯さん・午後は△△さん」のように**人＋時間帯を何組でも**付けられる（`attendance_exceptions.work_segments`）
- 🚨 勤怠の登録が DB に弾かれたら（`enforce_attendance_exclusive`）、**決定を止めて理由を出す**（中途半端に残さない）
- 休日出勤の残業申請は本人が出す

## 8. 決定のあと・休みの取り消し

- **決定を取り消す**（⑤）：決定で入れたもの（勤怠の登録・残業申請の依頼）を一覧で出し、1つずつ「取り消す／残す」を選ぶ。黙って消さない。
  代わりの人への取り消しのお知らせは ON/OFF。戻したあとは未調整に戻り、案を直してもう一度決定する
- **元の休み（休暇・欠勤）が取り消されたとき**
  - 決定前：調整の場を「元の休みが取り消されました」で**自動で閉じる**（コメントは残す）
  - 決定後：登録は消さず、調整の場に表示して①の権限の人に知らせる。代わりの登録を消すかは人が決める
- 🚨 「取消」以外に**差し戻し・行ごとの削除・受理済みの日付の変更（`admin_edit_leave_request`）・
  欠勤の「取消してこの内容で入力」（削除→入れ直し）**でも同じように動かす

## 9. 調整が要らなかったとき

- 調整の場で「**調整不要（変更なし）で閉じる**」（⑤）
- 状態を変えるのは調整の場だけ（カレンダーの印は表示と入口）

## 10. お知らせ

| いつ | 誰に | 設定 |
|---|---|---|
| 調整の場ができたとき | **送らない**（ユーザー確定） | — |
| 休みの3か月前・1か月前（既存 `remind-leave-shift-adjust`） | ①の権限の役職（既定）。管理画面で役職を指定すればそちらが優先 | 既存の設定（時期・時刻・前後の幅） |
| **休みが◯日以内なのに未調整（毎朝のまとめ・新設）** | 同上 | **何日以内（既定7日）／送る時刻（既定9時）／送る曜日／ベルだけにする**を管理画面で変えられる |
| 決定・決定の取り消し | 代わりに入る人 | 決定の画面で ON/OFF |
| パートへの依頼 | 依頼された本人 | 送るときに選ぶ |
| 依頼の返事の期限切れ | 送った人 | — |
| 意見の期限切れ | 案を作った人 | — |
| 決定の連絡（選ばれなかったパートへ） | 選ばれなかったパート | 文面は「この日の担当は決定しました。ご返事ありがとうございました。」既定は送らない（返事の画面に出すだけ）。送る設定も選べる |

- 🚨 **既存の「欠勤の登録」「休暇の受理」のお知らせは今のまま**（勤怠カレンダーへ飛ぶ）。
  そこから調整の場へは、カレンダーの印を押して入る。同じ出来事でスマホが2回鳴らないようにするための判断
- 休んだ本人には**調整の中身もお知らせも出さない**（Google カレンダーの予定で分かるため）
- 🚨 宛先を管理画面で指定しているときは、画面に「**見る権限とは別に指定中**」と出す（決める場所が2つになるため）
- 🚨 新しいお知らせは `notification_settings` の行（ベル・スマホ・メール）と `push-dispatch` の EVENT_MAP を必ず足す
  （行が無いと管理画面から止められない／EVENT_MAP に無い種類はスマホに飛ばされない）

## 11. 記録の掃除

- 調整の場の記録（コメント・案・確認・パートへの依頼と返事）は、**調整が終わって（決定・閉じた・過ぎた日）から90日で消す**。毎夜の cron
- 🚨 記録を消しても**調整の場の見出しの行（状態）は残す**（消すと未調整に戻り、お知らせが再び飛ぶ）
- 勤怠の登録・依頼への参照は `on delete set null`（依頼には既存の90日の掃除があるため）
- 容量：DB全体 41MB／調整の場は多めに見て年700件 → 90日保持で最大5MB程度（上限500MB）

## 裏取りした事実（2026-09-11〜12 実測）

- 勤怠カレンダーを開ける役職：リーダー4・マネージャー5・社長1・管理者1。パート18・一般12・フロア責任者5は開けない。URL 直打ちも塞がれている
- `leave_requests` の SELECT：本人・受理者1/2・管理者・社長、**および `is_leader_plus()` なら全件**
  → 調整の中身を `leave_requests` の列に置くと本人にも読まれる。**別の表にする**
- 🚨 `leave_requests` の `insert_own` は `auth.uid() = user_id` だけで**状態を見ていない**（守るトリガーも無い）
  ＝画面を通さなければ誰でも自分の休暇を受理済みで入れられる。**別の作業として切り出した**（2026-09-12）
- 休暇申請71件のうち**50件が有給奨励日**（本人が `status='approved'` で insert・1日最大20件）
- 調整休は `step2_pending` → `approved` に直行（マネージャー受理を通らない）
- `attendance_exceptions`：`attendance_input` の権限なら全操作、本人は自分の分を読める。欠勤39件のうち**9件は当日以降の登録**
- `weekly_shift_patterns` の SELECT：本人／管理者／`shift_pattern_directory`／`overtime_summary` の権限のみ
- 既存の `remind-leave-shift-adjust`：毎日動くが送るのは**休みの3か月前と1か月前に1回ずつ**。
  設定は `leave_shift_alert_settings`（1行：`enabled` / `months_before {3,1}` / `send_time 09:10` / `window_minutes 120`）。
  送信済みの印は休暇ごとに2列
- `push-dispatch` は EVENT_MAP に無い種類を送らずに飛ばす（2人共通の関数）
- スマホ通知を登録しているパートは **18人中6人**。パートの当日欠勤4件はすべて朝9時前の登録
- 機能権限で RLS を決める書き方（`has_feature_permission`）は既存ポリシー8件で使っている

## 作り方（レビューの提案を採用）

- **自動で作る仕組みは DB トリガー**に置く。受理は画面の複数経路・奨励日の insert・SECURITY DEFINER の関数を通るので、画面や Edge Function では漏れる
  - 休暇：`leave_requests` の INSERT／UPDATE（status・leave_dates・start_date・end_date・user_id）／DELETE
  - 欠勤：`attendance_exceptions` の INSERT／UPDATE（type・date・user_id）／DELETE
  - 両方から「その人・その日はまだ休みか」を数え直す**1つの関数**を呼び、作る／開き直す／自動で閉じる（何度動いても結果が同じ）
  - 🚨 トリガーの中の失敗で**受理そのものを巻き戻さない**（例外を受け止める。引き継ぎ (35) と同じ壊れ方を避ける）
  - 人と日の組で一意にする（同じ人・同じ日に休暇と欠勤が重なる例が本番に2件）。同じ日の休みが戻ったら新しく作らず開き直す
- **正しい状態は調整の場の表だけ**に持つ。`leave_requests.shift_adjust_status` は読むのをやめるか、要約を書き写すだけにする
- 相談の記録は `leave_requests` と**別の表**。見る許可に「**休んだ本人ではない**」を足す（管理者は例外）
- パートへの依頼は**さらに別の表**。見られるのは依頼された本人だけ。返事は RPC 経由（先着の取り合いは行を押さえて決める）。
  依頼の行に休んだ人の名前・休暇の種類を入れない
- 候補の一覧（週の基本シフトを含む）は、①を確かめる SECURITY DEFINER の RPC から返す（`weekly_shift_patterns` の許可は広げない）
- **決定の RPC**：⑤を関数の中で確かめる／調整の場の行を FOR UPDATE で押さえて二重決定を防ぐ／
  状態の更新・勤怠の登録・依頼を**1つの例外ブロック**に入れ、`enforce_attendance_exclusive`（23514）で弾かれたら全部取り消す／
  「指定した人が残業申請の権限を持つか」を DB で確かめる関数を新設（`has_feature_permission` はログイン中の本人しか判定できない）
- `gcal-sync` は DB から呼べない → 決定が確定したあと画面から呼ぶ。失敗したら「カレンダー未反映」の印と再実行ボタン
- 2人共通で触るもの：`useAuth.ts`（5つのフラグ）／`FeaturePermissionsTab.tsx`／`NotificationsTab.tsx`／
  `App.tsx`（CalendarPage に渡す値・通知から開く先・パートの返事画面のルート）／`push-dispatch`。**触る前に相手へ一声**

## 作る順番

1. 保留中のトリガー修正（引き継ぎ (35)）を適用
2. DB：調整の表・パートへの依頼の表・権限5つ（初期値は社長・管理者だけ）・RPC・RLS・掃除の cron・通知設定の行（お知らせは OFF で入れる）
3. 自動で作る仕組み（トリガー）

## この機能で特に効く決まり（CLAUDE.md より）

- 新しい関数は `revoke execute … from anon` を明示し、適用後に実際に呼んで確かめる
- 既存の関数を `create or replace` するときは**本番の実定義から起こす**
- 状態を持つので「**作る→消す→もう一度作る**」まで取り消し版で通してから完了と言う
- 記録を貯める表には**掃除の cron を同時に作る**
- 社内FAQと画面の注意書きも同時に直す／Edge Function を触ったら `npx deno check`
