# 計画：入社予定スタッフの登録・招待メール・パスワード変更の促し（2026-10-04〜）

申請系の担当が作る。共有ファイル（ログイン画面・AuthContext・管理画面・create-user など）は
**事後の連絡でよい**（2026-10-04 ユーザー明言・この件に限る）。連絡は `docs/引き継ぎ-場所予約.md` の「申請系からの連絡」へ。

## 1. 要望（ユーザー・2026-10-04）
- 新しいスタッフを、名前と入社日だけで先に登録し、入社日からのシフトを先に入れたい（メールはまだ分からないことがある）
- どこからログインするかを、登録したタイミングで本人のアドレスへ送る（登録のお願い・何のサイトか・通知の許可・ホーム画面に追加）
- または入社日の朝10時に届くように。メールが無ければ、入社後に聞いて入れ、保存するときに確認して送る
- 届いていないときは再送できる（管理者からも本人からも）
- 初期パスワードは推測できるものでもよいが、**初回ログイン時に変更を求める**。
  いまメールの頭のパスワードの人にも、管理画面から**変更依頼を一斉に送り**、ホームのバナー・ベル・メールで促す

## 2. 決まったこと（ユーザー確定）
| | 決定 |
|---|---|
| 自分で登録する入口（ログイン画面の新規登録） | **閉じる**（アカウントはすべて管理者が作る） |
| パスワード設定のメールの期限 | **1時間のまま**（本人が押した直後に届くため。切れたら押し直す） |
| Supabase のメール（送信上限）を通らない | パスワード設定のメールも**自前で Resend から送る**。「パスワードを忘れた場合」も同じ道にそろえる |
| 招待メールの文面 | 下の §5 で確定。使い道の1行は雇用形態で出し分け（パートは勤務変更の報告） |
| 共有ファイルの連絡 | 事後でよい |

## 3. 調べて分かったこと（エージェント2体のレビュー・本番で裏取り済み）
- 勤務表は `weekly_shift_patterns.user_id → auth.users`。シフト関係で利用者に外部キーを張る表が11以上ある
  → **「名前だけの人」を別の行で持つ案は大きすぎる。仮のアカウントで作る**
- `handle_new_user`（auth.users の insert トリガー）が、管理者が作った場合も経理へ「新規登録」の通知を飛ばす。
  名前は `raw_user_meta_data->>'name'` だが create-user は `full_name` で渡している
  → 止める印は **app_metadata**（本人が signUp で書ける user_metadata に置くと誰でも止められる）
- **有効化（is_active=true）する前にパスワード設定のリンクを開いても、AuthContext が追い出してパスワードを決められない**
  → 招待メールには期限のあるリンクを入れない。本人がログイン画面の［はじめての方］を押したときに設定のメールを送る
- 会社のメールの安全確認（Safe Links など）が1回きりのリンクを先に使う事故がある
  → メールのリンクは `token_hash` を持つページを開くだけ。ページの［パスワードを決める］を押して初めて `verifyOtp` する
- `lib/retire.ts` の retireState は「is_active=false で pending でない＝退職済み」。入社予定の分岐が要る
- シフト管理の読み込みは is_active で絞っている（`shiftRosterApi.ts:45`・cleaning/kids/study の各 API）→ 入社予定も出す
- 初期パスワードは UsersTab がメールの @ より前を自動で入れる。profiles は全員が全行を読める（"authenticated users can read all profiles"）
- create-user は approval_status を書かない（トリガーの 'pending' が残る）

## 4. 作り
### 4-1. 状態（判定は `client/src/lib/staffState.ts` と DB の `my_access_state` だけ）
- **入社予定** ＝ `is_active=false` かつ `hire_date` あり かつ `retired_at` なし かつ approval_status ≠ 'pending'
- 入社日の 0:01（JST）に cron `hire-daily` が `is_active=true` にする（1人ずつ失敗を受け止める）。
  入社日を過ぎても入社予定のままなら「切り替えに失敗」（退職の switch_failed と同じ考え方）
- 入社予定のあいだ：ログインすると「◯/◯（入社日）から使えます」。通知の宛先・連絡板・安否・受理先には出ない（is_active で既に外れる）。
  **シフト管理（勤務表・掃除・勉強会・こども）には出す**

### 4-2. DB（migration 1本）
- profiles に列：`hire_date` / `invite_scheduled_for` / `invite_sent_at` / `invite_send_count` / `invite_claimed_at` /
  `must_change_password` / `pw_change_requested_at` / `setup_mail_last_at` / `setup_mail_day` / `setup_mail_count`
- `handle_new_user`：app_metadata の `provisioned_by_admin` があれば通知を飛ばさない／名前は name か full_name／search_path
- `my_access_state`：入社予定なら `{mode:'prehire', hire_date}`
- `hire_daily()` と cron `hire-daily`、招待の cron `staff-invite-due`（15分ごと・送るものがあるときだけ関数を呼ぶ）
- `clear_my_password_flag()`：本人がパスワードを変えたあと印を消す（anon から外す）
- 🚨 RPC・トリガーは本番の実定義から起こす

### 4-3. Edge Function
- **`staff-onboard`**（管理者だけ。send_due は service_role だけ）
  - `create`：名前・雇用形態・役職・入社日・メール（任意）・送るタイミング（now / hire_date / none）
    メールが無ければ仮のアドレス（`.invalid`）。パスワードはランダム。app_metadata に印
  - `update`：入社日の変更（送信予定も動く）・メールの差し替え（`updateUserById`）・送るかどうか
  - `send`：今すぐ送る／再送（1日3回まで）
  - `request_password_change`：選んだ人に印＋ベル＋メール
  - `send_due`：送信予定を過ぎた人へ送る（取り押さえてから送る＝二重に送らない）
- **`password-setup-mail`**（ログイン前に呼ぶ・誰でも）
  - 在籍（is_active=true）の人のアドレスなら `generateLink(recovery)` の `hashed_token` で `/reset-password?token_hash=…` を作り Resend で送る
  - 同じアドレスへは1分に1回・1日5回まで。**アドレスが登録されているかどうかで返事を変えない**
- `send-email`：`.invalid` 宛ては送らない
- `create-user`（既存の「ユーザー追加」）：approval_status を明示・app_metadata の印・`must_change_password=true`

### 4-4. 画面
- ログイン画面：新規登録をなくす／［はじめての方・パスワードを忘れた方］を新しい関数に／入社予定の人の文言
- `/reset-password`：`token_hash` があれば［パスワードを決める］→ verifyOtp → 新しいパスワード。成功したら印を消す
- パスワードの変更（ChangePassword）：成功したら印を消す
- ホーム：印がある人に「パスワードを変更してください」のバナー（変えるまで出る）
- 管理画面「ユーザー」：［入社予定の人を登録］／入社予定の一覧（入社日・招待の状態・［再送］・メールを入れる・入社日を変える・取り消す）／
  ［パスワード変更の依頼を送る］（選んだ人・全員）
- シフト管理の読み込み 4本：入社予定の人も出す

## 5. 招待メールの文面（ユーザー確定・2026-10-04）
件名：【ファイブM】スタッフサイトへの登録のお願い

> {名前}さん
>
> ファイブMの社内スタッフサイトに、{名字}さんのアカウントを用意しました。
> {正社員：社内の連絡、交通費・残業の申請などに使います。／パート：社内の連絡、交通費の申請、勤務変更の報告などに使います。}
> 入社日（{m/d（曜）}）から使えますので、必ず登録をお願いします。
>
> ■ 登録のしかた（{m/d（曜）}から）
> ① https://fivem-portal.vercel.app を開く
> ② ［はじめての方（パスワードを決める）］を押し、このメールアドレス（{メール}）を入れる
> ③ 届いたメールのボタンからパスワードを決め、ログインする
>
> ■ スマートフォンのホーム画面に追加（通知を受け取るために必要です）
> iPhone：Safari の下の共有ボタン（□に↑）→「ホーム画面に追加」→ 追加されたアイコンから開き直す
> Android：Chrome の右上の ⋮ →「ホーム画面に追加」
> ※ LINE の中で開いた場合は、メニューから「Safari で開く」を選んでください
>
> ■ 通知の許可
> アイコンから開いたあと、右上のアイコン →「アカウント設定」→「許可する」
>
> ■ メールが届かないとき
> パスワードのメールは1時間有効です。過ぎたときや届かないときは、もう一度［はじめての方］を押してください。
> ご不明な点は、マネージャーまでお問い合わせください。

（問い合わせ先の一文は 2026-10-04 に「管理者」→「マネージャー」へ変更。全部のメールで同じ `CONTACT_LINE`）

入社日を過ぎてから送るときは「入社日（…）から使えますので、」→「」、「（{m/d}から）」→「」にする。

## 6. ほかの文言（2026-10-04 ユーザー確定・実物は supabase/functions/_shared/staffMail.ts と画面）
- **パスワード変更のお願い**：送るときに理由を選ぶ（profiles.pw_change_reason）
  - initial＝初期パスワードのままの方へ（［＋ ユーザー追加］で作った人にも自動でこれ）
  - review＝安全のための見直し（全員へ）
  - バナー：「パスワードの変更をお願いします」／「パスワードの見直しをお願いします」＋お願いの説明＋「変更するとこのお知らせは消えます」（閉じるボタンなし）
  - ベル：「🔑 パスワードの変更をお願いします」／「🔑 パスワードの見直しをお願いします」
  - メール：件名「パスワード変更のお願い」／「パスワード見直しのお願い」。initial には「すでに変更済みの方も、もう一度」の一文
    （こちらから誰が変えたか見分けられない・今と同じパスワードには変えられないため）
- **パスワード設定のメール**：件名「パスワード設定のご案内」。リンクを開くと［パスワードを決める］の画面
- **入社日より前**：［はじめての方］→「スタッフサイトは入社日から使えます」のメール／ログイン→「このアカウントは入社日（m/d）から使えます。当日、［はじめての方（パスワードを決める）］から…」
- **ログイン画面**：［はじめての方（パスワードを決める）］（新しく）・「パスワードを忘れた場合」（今のまま）・
  「アカウントは会社が用意します。案内のメールが届いていない方は、マネージャーにお知らせください。」
  はじめての方の説明：「パスワードを決めるためのメールを送ります。ご自身のメールアドレスを入れてください。」
  送ったあと：「このメールアドレスが登録されていれば、…」（登録の有無を出さない）

## 7. 出す順番
① DB → ② Edge Function（git pull・deno check）→ ③ 画面の push。
仮のアドレス（`.invalid`）が GoTrue で通るかは、トリガーを直したあとに1回だけ作って消して確かめる（本番・許可を得てから）。
Supabase の管理画面で「新規登録を許可する（Allow new users to sign up）」をオフにする（ユーザーが操作。管理者の作成は影響を受けない）。
