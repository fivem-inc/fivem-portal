## 1. いまの作り（2026-09-18 調査）

- 退職は `profiles.is_active = false` の1つだけ（`20260529000000_add_is_active_to_profiles.sql`）。**退職日の列は無い**
- 🚨 `is_active = false` は**承認待ち**の人にも使われている（区別は `approval_status = 'pending'`・`AuthContext.tsx:37,72`）
- 管理画面：ユーザー管理の各行に「退職／復活」。押すと `profiles.is_active` を反転するだけ（`AdminPanelContext.tsx:630-636`）。退職者にだけ「削除」（Edge Function `delete-user`）
- ログインの門：`AuthContext.tsx` の `applySessionUser` だけ。is_active=false なら signOut して「このアカウントは無効です」
  - 🚨 穴①：同じ人の確認は2回目以降スキップ（`:42`）、TOKEN_REFRESHED でも確認しない（`:145-149`）
    → **ログイン中に退職にされた人は、ログインし直すまで使い続けられる**
  - 🚨 穴②：Supabase Auth の段階では弾いていない。トークンは有効なので、API を直接呼べば RLS の範囲で読み書きできる
- RLS：連絡板・休暇・カレンダーなどは **is_active を見ていない**。交通費（expenses）と残業（overtime_reports）の本人の読み書きも見ていない
- `is_active = true` で「在籍者だけ」に絞っている場所が数十か所ある：通知・一斉リマインドの宛先、決裁者の自動選出、シフト表・掃除当番、Edge Function（announcement-notify / announcement-remind / remind-scheduled / remind-overtime-* / safety-check-send）など
  → **退職者に通知が飛ばないのは、この絞り込みのおかげ**
- 残業の集計（部門集計）は「その期に行がある人」を id で解決しており、**退職者も出る**（`OvertimePage.tsx:2853` のコメント）。
  🚨 経理の Excel・残業の管理タブのスタッフ一覧（`OvertimeAdminTab.tsx:591` は `is_active = true`）は**要確認**
- 日付で自動的に退職へ切り替える仕組みは**無い**

## 2. 決まったこと（2026-09-18 ユーザー確定）

| 項目 | 決定 |
|---|---|
| 骨組み | **退職はいまのまま（is_active=false）**＋「**申請できる期限**」を足す。権限管理に「**退職者**」の列を1つ足す |
| 退職日の予約 | 管理画面で退職日を入れておくと、その日の0時（JST）に自動で退職に切り替わる |
| 期限の初期値 | **退職日が入る給与期間の締め（支給月17日）**。例：10/31 退職 → 10/16〜11/15 → **12/17 まで**。人ごとに直せる |
| 最初から ON にする機能 | **交通費・残業・勤務変更報告** |
| 退職者への通知 | **送らない**（自分の申請の受理・差し戻しも） |
| 退職者の残業 | **集計と経理の Excel に入れる**（給与に関わる） |
| 穴 | **塞ぐ**：ログイン中に退職にされた人を止める／連絡板などは DB 側でも退職者から隠す |

### 状態の整理
| | 在籍中 | 退職後〜期限 | 期限のあと |
|---|---|---|---|
| is_active | true | false | false |
| ログイン | できる | **できる（限られた画面）** | できない |
| 使える機能 | 役職の権限どおり | 権限管理の「退職者」列で ✓ のものだけ | — |
| 通知・宛先・一斉連絡 | 入る | 入らない（今の is_active の絞り込みのまま） | 入らない |

### なぜ「退職」の意味を変えずに期限を足すのか
- 通知・宛先・決裁者・シフト表などで `is_active = true` を見ている数十か所を**触らずに済む**（触れば必ずどこかが漏れる）
- 「退職者」という**役職**を作る案は採らない：役職を書き換えると元の役職（マネージャーだった等）の記録が消え、役職の属性（承認者・序列）も変わる

## 3. 作りの案（レビューで確かめてもらう）

### データ
- `profiles.retire_date date`（退職日・予約を含む）
- `profiles.retiree_access_until date`（申請できる期限。null＝退職日から計算した初期値を使う）
- 退職者に許す機能：`feature_permissions` は役職（role_id）が必須なので使えない。
  → `app_settings.retiree_feature_keys`（文字の配列・初期値 `['expense','overtime','shift_report']`）
- 判定関数（DB）：`is_retiree_in_grace(uid)`＝is_active=false かつ retire_date あり かつ 今日 <= 期限 かつ 承認待ちではない
- 🚨 承認待ち（approval_status='pending'）は退職者と取り違えない（retire_date が無ければ退職者ではない）

### 自動の切り替え（cron）
- 毎日 0:05（JST）：`retire_date <= 今日 かつ is_active = true` の人を `is_active = false` にする
- 期限を過ぎた人は、判定関数が false を返すのでログインできなくなる（切り替え不要）
- 🚨 記録を貯める仕組みではない（掃除は不要）

### ログインの門（AuthContext）
- is_active=false でも `is_retiree_in_grace` が true なら通す（**限定モード**）
- 穴①を塞ぐ：TOKEN_REFRESHED・画面に戻ったとき（visibilitychange）にも状態を読み直し、退職（期限切れ含む）になっていたら signOut

### 権限（useAuth）
- 限定モードでは、`retiree_feature_keys` に入っている機能だけ true、**それ以外はすべて false**（上長向けの機能は常に false）
- 役職プレビューとの関係を決める（プレビューに「退職者」を足すか）

### DB（穴②を塞ぐ）
- 共通の関数 `is_current_staff()`＝在籍者（is_active=true）または管理者
- 連絡板（board_messages / board_channels / board_message_recipients / board_reads / board_confirmations 等）・休暇・カレンダーなどのポリシーに「在籍者だけ」を足す
- 交通費・残業・勤務変更報告の本人のポリシーは、**在籍者 または 期限内の退職者**（期限を過ぎたら書けない）
- 🚨 どの表に足すかはレビューで洗い出す（漏れると「画面は隠れているが API で読める」が残る）

### 画面
- ユーザー管理：各人に「退職日」「申請できる期限」（初期値を表示）と［退職日を取り消す］。状態の札「在籍中（10/31 退職予定）」「退職・申請期間中（12/17 まで）」「退職」
- 権限管理：表に「退職者」の列。上長向けの機能の行は「―」（押せない）
- 退職者の画面：ナビは ✓ の機能だけ。上に黄色で「退職後の申請期間です（12/17 まで）。残業・交通費などの申請だけできます。」

### 通知
- 退職者には送らない。いまの `is_active = true` の絞り込みで自然に外れる
- 🚨 直送（キューを通らない）通知・`notifications` への直接 insert で、退職者に届く経路がないか洗い出す

### 残業の集計・Excel
- 部門集計は退職者も出る（確認済み）
- 🚨 経理の Excel・残業の管理タブの一覧で、退職者が抜けないか確認して直す
