### 状態の整理
| | 在籍中 | 退職後〜期限 | 期限のあと |
|---|---|---|---|
| is_active | true | false | false |
| ログイン | できる | **できる（限られた画面）** | できない |
| 使える機能 | 役職の権限どおり | 権限管理の「退職者」列で ✓ のものだけ | — |

### なぜ「退職」の意味を変えずに期限を足すのか
- 通知・宛先・決裁者・シフト表などで `is_active = true` を見ている数十か所を**触らずに済む**（触れば必ずどこかが漏れる）
- 「退職者」という**役職**を作る案は採らない：役職を書き換えると元の役職（マネージャーだった等）の記録が消え、役職の属性（承認者・序列）も変わる

## 3. 作りの案（レビューで確かめてもらう）

### データ
- `profiles.retire_date date`（退職日・予約を含む）
- `profiles.retiree_access_until date`（申請できる期限。null＝退職日から計算した初期値を使う）
- 退職者に許す機能：`feature_permissions` は役職（role_id）が必須なので使えない。
  → `app_settings.retiree_feature_keys`（文字の配列・初期値 `['expense','overtime','shift_report']`）
- 判定関数（DB）：`is_retiree_in_grace(uid)`＝is_active=false かつ retire_date あり かつ 今日 <= 期限 かつ 承認待ちではない
- 🚨 承認待ち（approval_status='pending'）は退職者と取り違えない（retire_date が無ければ退職者ではない）

### 自動の切り替え（cron）
- 毎日 0:05（JST）：`retire_date <= 今日 かつ is_active = true` の人を `is_active = false` にする
- 期限を過ぎた人は、判定関数が false を返すのでログインできなくなる（切り替え不要）
- 🚨 記録を貯める仕組みではない（掃除は不要）

### ログインの門（AuthContext）
- is_active=false でも `is_retiree_in_grace` が true なら通す（**限定モード**）
- 穴①を塞ぐ：TOKEN_REFRESHED・画面に戻ったとき（visibilitychange）にも状態を読み直し、退職（期限切れ含む）になっていたら signOut

### 権限（useAuth）
- 限定モードでは、`retiree_feature_keys` に入っている機能だけ true、**それ以外はすべて false**（上長向けの機能は常に false）
- 役職プレビューとの関係を決める（プレビューに「退職者」を足すか）

### DB（穴②を塞ぐ）
- 共通の関数 `is_current_staff()`＝在籍者（is_active=true）または管理者
- 連絡板（board_messages / board_channels / board_message_recipients / board_reads / board_confirmations 等）・休暇・カレンダーなどのポリシーに「在籍者だけ」を足す
- 交通費・残業・勤務変更報告の本人のポリシーは、**在籍者 または 期限内の退職者**（期限を過ぎたら書けない）
- 🚨 どの表に足すかはレビューで洗い出す（漏れると「画面は隠れているが API で読める」が残る）

### 画面
- ユーザー管理：各人に「退職日」「申請できる期限」（初期値を表示）と［退職日を取り消す］。状態の札「在籍中（10/31 退職予定）」「退職・申請期間中（11/30 まで）」「退職」
- 権限管理：表に「退職者」の列。上長向けの機能の行は「―」（押せない）
- 退職者の画面：ナビは ✓ の機能だけ。ホームは**いつものホーム**（§4-6）。上に黄色の案内（文言は §4-4）

### 通知
- 🔁 期限内の退職者には**本人あての受理・差し戻しだけ**通常どおり送る（§2 の表）。それ以外はいまの `is_active = true` の絞り込みで外れる
- 🚨 push-dispatch などが is_active で本人あてを落としていないか要確認（落としていれば「期限内の退職者は通す」を1か所に足す・共用なので事前連絡）
- 🚨 直送（キューを通らない）通知・`notifications` への直接 insert で、退職者に届く経路がないか洗い出す

### 残業の集計・Excel
- 部門集計は退職者も出る（確認済み）
- 🚨 経理の Excel・残業の管理タブの一覧で、退職者が抜けないか確認して直す

## 5. 🚨 レビューで見つかった穴（2026-09-18 夜に本番で実測・裏取り済み）

### 5-1. 役職を判定する DB の関数が「在籍中か」を見ていない
本番の関数定義を読んで確かめた。`is_active` を見ていないもの：
`role_is_manager_plus` / `role_is_leader_plus` / `role_is_approver` / `role_is_board_approver` /
`role_is_org_wide` / `role_acts_as` / `role_rank` / `has_feature_permission` / `user_has_feature_permission` /
`room_is_staff`（場所予約・相手の担当）
（見ているもの：`is_manager_plus()` / `is_leader()` / `profile_ids_for_roles` / `resolve_role_recipients` / `overtime_visible_roster`）

- いまは退職者がログインできないので実害は無い。**申請期間でログインできるようにした瞬間に穴になる**。
  例：マネージャーだった人が退職後にログインすると、RLS が `role_is_manager_plus(auth.uid())` で
  部下の申請・全体の集計を読める／受理できる
- 直し方の方向：関数の中に「在籍者であること（is_active=true）」を足す（**関数側で1か所**。呼ぶ側のポリシー数十か所は触らない）
- 🚨 `has_feature_permission` に足すと、退職者の ✓ の機能（交通費など）も false になる。
  → 退職者の許可は**別の関数**（`is_retiree_in_grace` と `retiree_feature_keys`）で見る。混ぜない
- 🚨 `room_is_staff` は場所予約の担当の関数。**触る前に相手に連絡**（第2部 §2）
- 🚨 すべて create or replace は**本番の実定義から起こす**

### 5-2. 本人あての通知が退職者を外していない
次の Edge Function は申請者本人に送るが、`is_active` を1回も見ていない（grep で0件）：
`overtime-approve` / `leave-approved-notify` / `shift-report-confirmed-notify` / `shift-report-returned-notify` /
`time-adjustment-notify` / `purchase-reimbursement-notify` / `send-rejection-email`

- 🔁 決定が「期限内は本人あての受理・差し戻しを送る」に変わった（§2）。
  → この7本は**期限を過ぎた退職者**（と、期限を持たない昔の退職者）に送らないよう、送り先を決めるところで判定する必要がある
- 🚨 1本ずつ書くと漏れる。共通の判定（例：push-dispatch の手前、または `notifications` への insert を
  在籍者だけにする1か所）に寄せられないかを実装前に調べる
- 🚨 `push-dispatch` / `send-email` は**2人で共用**。触るなら事前に連絡・`deno check`・deploy 前に `git pull`
- 🚨 退職者の通知を止めると、差し戻しに本人が気づけない → §4 の 5 で決める

## 6. 🆕 退職の手続きのチェック（2026-09-18 夜 ユーザー依頼・未設計）

依頼：退職者が出たとき、**Slack・Google カレンダーなどの設定解除をいつも忘れる**。
マネージャーが漏れなくできるように、必須事項のチェックも含めて仕組みにしたい。

### 調べて分かったこと
- ポータルは Slack・Google のアカウントを**人ごとに持っていない**（列は `profiles.email` だけ。
  Slack は Webhook でチャンネルに送るだけ、Google カレンダーは共有カレンダーに予定を書くだけ）
  → **外部の解除はポータルからは自動でできない**。人がやったことを「チェック」で残す形になる
- ポータルの中にも「その人を名指しした設定」がある（連絡板の代表者CC・グループのメンバー・
  宛先の除外・確認者の既定・リーダー割り当てなど）。これは**ポータルが自動で見つけて一覧にできる**
  （どの設定を見るかは実装前に洗い出す）

### 作りの案（たたき台・未決定）
- **チェック項目は管理画面で管理者が編集**（例：Slack の解除／Google アカウントの停止／
  カレンダーの共有解除／鍵・備品の返却 …）。「必須」の印を付けられる
- 退職日を入れると、その人の**チェック表**ができる。各項目に「済み（誰が・いつ）」を残す
- ポータル内の名指し設定は、同じ表に**自動で並べる**（直す画面へのリンク付き）
- 必須が残っている間は、担当マネージャー（と管理者）に**残っている件数**を出す
  （🚨 押して消せない赤いバッジにしない＝備品購入申請で踏んだ失敗。出し方は要相談）
- 🚨 記録を貯めるので**掃除も一緒に作る**（例：アカウントを削除したら消す／完了から◯年で消す）
- 🚨 新しい通知を足すなら**宛先を必ず絞る**（「設定が無い＝全員に送る」作りのため）

### 8-1. 前提（本番で実測）

### 8-2. やり方の選択肢
**案A：1つずつ締める（これまでの設計書の方針）**
- 44表のポリシーに「呼ぶ人が在籍」を足す／121本の関数の入口に在籍の判定を足す／管理者の判定88か所を見直す
- 🚨 量が多く、1つでも漏れると「画面は隠れているが API で読める」が残る。3段目のあとも、新しい表・関数を作るたびに足し忘れる

**案B（推奨）：退職者だけ「別の DB の役割」でログインさせる（最初から何も使えない＝許したものだけ使える）**
- DB に退職者専用の役割（例：`retiree`）を作る。**表の権限は何も持たない**（PUBLIC への表の許可は0なので、初めから全部読めない）
- ログインの鍵（JWT）を作るときに、期限内の退職者だけ役割を `retiree` にする（Supabase の「Custom Access Token Hook」）
- `retiree` に許すのは、申請に要る表と関数だけ（交通費・残業・勤務変更報告の本人の行／申請画面が読む選択肢・カレンダー・役職など）
- 関数：PUBLIC への実行許可（258本）を外し、anon・authenticated・service_role に**今と同じものを個別に付け直す**（在籍者は何も変わらない）。
  `retiree` には申請に要る関数だけを許す
- 良い点：**新しい表・関数を足しても、退職者には自動で閉じたまま**。在籍者のポリシー88か所・関数121本を触らずに済む
- 注意：
  - Hook の設定は Supabase の管理画面（または config.toml の `[auth.hook]`）で有効にする必要がある
  - 🚨 Hook が失敗するとログインが全員止まる → Hook の中は例外を必ず受け止め、失敗したら通常どおり authenticated にする
  - `retiree` に許すポリシーは `to retiree` で別に書く（在籍者のポリシーは触らない）
  - Edge Function（service_role で動く）は役割を見ないので、別に呼ぶ人の在籍を確かめる（レビュー §7-2 の overtime-approve・receipt-signed-url など）

### 8-3. 案Bでも案Aでも要るもの
- 退職の確定時（retire_apply）に：app_metadata の role（管理者）を外す／その人のセッションを消す（ログイン中の人を止める）
- 期限切れ（毎晩）：ログインを止める（banned_until）＋プッシュの登録を消す
- AuthContext：TOKEN_REFRESHED・画面に戻ったときにも状態を読み直す（ログイン中に退職になった人を止める）
- 🚨 auth.users・auth.sessions を SQL から書き換えてよいかは、取り消し版で確かめてから

### 8-4. 安全に出す手順（シニアエンジニアの提案）
1. 変える前に `pg_policies` と関数の権限（proacl）を丸ごと保存し、戻し版の SQL を用意する

### 8-5. ✅ 決定（2026-09-19）：**案B（退職者だけ別の DB の役割）**で進める

6. ここまで出してから3段目（画面の限定モード）
