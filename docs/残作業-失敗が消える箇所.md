## 何が問題か

🚨 **supabase の `.update()` / `.delete()` は、RLS（権限）で弾かれても
error にならず「0件成功」で返る。** 戻り値を受けないと、
何も更新できていなくても先へ進んでしまう。

2026-09-09 に実際に起きていたこと：
- 受理が通っていないのに、申請者へ「受理されました」と通知が飛んでいた
- 更新できていないのに、Googleカレンダーの予定が削除されていた

## 直し方（決まった形）

```ts
import { describeUpdate } from '../lib/statusUpdate';   // パスは階層に合わせる

const res = await supabase.from('テーブル').update({ … }).eq('id', id).select('id');
const fail = describeUpdate(res, '受理', 'missing');   // 'competing' との使い分けは下記
if (fail) { setErrorMsg(fail); return; }
```

- `missing` … 権限が無い／対象が消えた（→ 管理者に相談。自分では直せない）
- `competing` … 他の人が先に処理した（→ 一覧を更新して確認）
- 🚨 この2つは**利用者が次にすべきことが正反対**なので混ぜないこと

【`.eq('status', …)` を足すかどうか】
　そのボタンが**特定の状態のときにしか画面に出ない**なら足してよい（挙動は変わらない）。
　管理者の是正操作など、どの状態からでも押せるものには足さない（管理者が詰む）。

【順序】
　🚨 **失敗したときに「もう一度押せば直る」順序にする。**
　　 例：関連する行を消すとき、一覧に出す元になっている行（＝対象）を**最後に**消す。
　　 先に消すと、残りが中途半端に残ったまま一覧から消えて、直す手段が無くなる。

【lint】
　`client/eslint.config.js` に「戻り値を受けない update/delete」を禁止するルールがある。
　🚨 片付いたファイルを `files:` に**足していく**こと（足す前に0件を確認）。

## 別枠：`.then(null, () => {})`（54件）

🚨 **一括で置換しないこと。** 受け手によって意味が真逆です。

- 受け手が **supabase のビルダー** → エラーを拾えていない（直す対象）
- 受け手が **素の async 関数**（`dispatchEmail` など）→ **正当な守り**。外すと未処理エラーになる

判定は目視ではなく、受け手を機械で辿ること。
