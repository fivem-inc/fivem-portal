# 計画（案）：経理向け「あとから変わった申請の一覧」（2026-10-26）

## きっかけ（ユーザーとの話）
- 経理は給与期間（16日〜翌15日）のデータを、15日より前（例：10日）や16日に取り出して計算を始めることがある。
  そのあとで本人・上長が申請を変えると、経理の手元の数字と食い違い「なぜ変わった？」になる。
- 決まったこと（2026-10-26 ユーザー）：
  - 16日・17日に本人・上長の変更を**止めない**（経理も同じアカウントを使っている・知らせが届けばよい）。今の「締め後アラート」（残業の本人取消・振替休日の変更）はそのまま
  - 経理の「計算を始めた」ボタンは**作らない**（変わったものが見えれば足りる）
  - **経理向けに「あとから変わった申請」を一覧で見られる画面を作る**（必要）

## 今の記録で足りないこと（2026-10-26 本番で数えた）
- overtime_report_history：本人の報告・取消・管理者の修正は残る。**上長の受理・差し戻しは残らない**（Edge Function overtime-approve は「代わりに受理」のときだけ書く）
- leave_request_history：管理者の修正（admin_edit_leave_request）のときだけ。この30日は0件。受理の4段・取消は残らない
- shift_report_history：あり（中身の範囲は要確認）
- application_deletion_log：削除は残る（2026-10-23〜）
→ 既存の履歴を集めるだけでは「いつ・だれが受理した／取り消した」が抜ける

## 案
### 記録（DB）
- 新しい表 `application_change_log`：申請が変わるたびに1行（だれの申請・どの申請・種類（残業／休暇／勤務変更）・対象日・給与期間・何が起きたか（新規・受理・差し戻し・取消・実績報告・確定・修正・削除）・前と後（状態・時間数の差分・日付・種類）・した人・日時）
- 書くのはトリガー（overtime_reports・leave_requests・shift_reports の INSERT／UPDATE。状態・日付・時間数・種類が変わったときだけ）。画面・Edge Function を直さなくても全部の道（1件フォーム・表入力・まとめて申請・受理・管理者の修正・cron）が記録される
- 削除は既存の application_deletion_log を一緒に読む
- 読めるのは管理者だけ（RLS）。書けるのはトリガーだけ。🚨 新しい表なので GRANT を同じ migration に（2026-10-30 からの Supabase の変更）
- 🚨 掃除：毎晩の cron で3年より古い行を消す（DB の無料枠 500MB の決まり）。1日の行数の目安：今の更新は残業 約300件／30日・休暇 約30件／30日＝1日数十行

### 画面（管理画面・管理者だけ）
- 置き場所：管理画面の新しいタブ「変更の記録」（または「修正依頼」タブの中の新しい区切り）
- 絞り込み：給与期間（今の期・前の期）／「◯月◯日 ◯時より後」／申請の種類／人
- 並び：新しい順。1行＝日時・名前・申請（種類・対象日）・何が起きたか・前 → 後（時間数の差など）・した人
- 「ここまで見た」印（経理が押す）：次に開いたとき、それより新しい行に印。経理のアカウントは共用なので印は1つ
- Excel に出す（経理が手元の計算と突き合わせるため）

### 知らせ
- 今ある「締め後アラート」（16〜17日の本人取消・振替休日の変更）はそのまま
- （要相談）締め後アラートを休暇・勤務変更にも広げるか

## 見てほしいこと
- 経理が「データを取ったあとに何が変わったか」を迷わず・見落とさず確かめられるか
- 記録の作り方（トリガー）で漏れ・二重・重さ（DB の大きさ・速さ）が出ないか。今あるトリガー（シフト調整・お知らせ・二重計上の見張りなど）とのぶつかり
- 2人共通のファイル（AdminPanel.tsx・AdminPanelContext.tsx）を触る量

## レビュー（UI/UX・シニアエンジニアの2体・2026-10-26）で決め直したこと
### 記録（DB）
- 新しい表に記録する方針はそのまま（今の履歴表は申請と一緒に消える・受理が残らない・書き込みの失敗で黙って抜けるため使わない）
- 🚨 「した人」：Edge Function（受理・差し戻し・取消・勤務しなかった・振替休日の変更）はサーバーの鍵で書くので、トリガーではだれか分からない
  → した人を決める関数を1つ作る（ログインした人／関数の中で置く印 app.actor_id／Edge Function が付ける見出し）。削除の記録も同じ関数に。管理者は共用なので「管理者（共用）」と出す
- トリガーは AFTER（ほかの見張りが最後に直した値を残す）・見る列を絞る（cron が毎日書く通知の時刻などは数えない）
- 🚨 記録の失敗で申請の保存を止めない（読めない値は受けて「記録の失敗」の行を残す）
- 休暇から自動でできる時間外調整休の行（leave_auto）は記録しない（休暇の1回の操作で「削除＋新規」の雑音になる）
- 給与期間は「前と後の全部の日の期間」を持つ（休暇は2つの期にまたがる・日付を動かすと期が変わる）
- 外部キーは張らない（申請を消しても記録は残す）。止める印（大きな直しの SQL 用）。権限は削除の記録と同じ形＋ GRANT（10/30 前後どちらでも同じ結果）
- 1行＝約1KB・1か月約900行・3年で約30MB。掃除は毎月1回（3年より古い行）
- 過去の分は作れない（受理の記録がもともと無い）→ 画面に「◯月◯日から記録」

### 読む処理
- 🚨 結果を1つにまとめて返す（1000件で黙って切れないように）。削除の記録も一緒に。日本語の札（受理・差し戻しなど）は読む処理の1か所で作る

### 画面
- 最初の見方は「人ごと（従業員番号の順）→ 対象日の順」のまとめ。行を開くと経過。時系列は切り替えで
- 既定は「給与の数字が変わるもの」だけ（新規・取消・削除・差し戻し・時間数・日付・種類の変更・最終の受理）。途中の段（休暇の受理の途中など）は「状態だけ ◯件」でたたむ
- 期をまたぐ変更は両方の期に出す（札「別の期へ移動」）。締めた期（支払い済み）への変更は上に赤い枠で別に
- 「ここまで確認した」の印は「画面に出ていたいちばん新しい行の時刻」で残す（押した時刻ではない）。絞り込みで隠れた新しい行があれば知らせる。1つ前に戻せる。置き場所は未確認の行のいちばん下。「前回の確認：10/14 15:20（18件）」
- 状態の呼び名が画面ごとにずれている（削除の記録・修正依頼）→ 先に lib の1か所にまとめる
- 締め（17日）以降の変更に「締め後」の札
- Excel：シート「変更の一覧」（1行＝1つのできごと・時間数は分の整数）と「人ごとの差」

## ユーザーの決定（2026-10-26）
1. 置き場所：管理画面の新しいタブ（削除の記録もこちらへ移す）
2. 経理の計算は「受理済み」だけ → 一覧の既定は「受理済みの数字が変わったもの」＝受理になった／受理済みが取消・削除・差し戻し・修正された。受理の前だけの動き（申請中の直し・途中の段）はたたむ
3. 最初に出す期間：今の給与期間
4. Excel を出した時刻を「確認した印」として自動で残す
   → 経理が給与のために出す Excel・CSV（残業・勤務変更の［表で見る］の Excel・一覧の出力・交通費）と、この画面の Excel。出した時刻を給与期間ごとに残し、それより後の変更に印（出力の中身は変えない）
5. 対象：残業・休暇・勤務変更に加えて、勤怠カレンダーの予定（attendance_exceptions・受理が無いので入れた時点で確定）と交通費（受理済みになったもの以降）
6. 文言：3案とカラーのモックで決める

## 文言（2026-10-26 ユーザー確定：すべて案B）
- タブ名：📋 受理済みの変更（削除の記録もこのタブへ・受理の前に消したものはたたむ）
- 見出し：給与期間 10/16〜11/15 の変更
- 黄色の1行：10/14 15:20 にデータを出したあと、4件 変わりました

  そのあと変更が無いとき「10/14 15:20 にデータを出したあとの変更はありません」／まだ一度も無いとき「この給与期間は、まだ確認済みにしていません（変更 ◯件）」
- 青いボタン：［確認済みにする］
- 0件のとき：この給与期間に、受理済みの申請の変更はありません。
