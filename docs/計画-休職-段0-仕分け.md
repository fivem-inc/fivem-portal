# 計画：休職 段0「在籍で絞っている所」の仕分け（2026-10-19・調べただけ・コードと DB は変えていない）

🚨 公開リポジトリ。個人名・メールアドレスは書かない（コードの場所と役割だけ）。
もとの計画：`docs/計画-休職と手続き.md`（「レビューの結果」）。

## 前提
- 休職中の人は `profiles.is_active = true` のまま（ログインできる）。新しく `profiles.on_leave`（boolean）を足す予定。
- 休職中は **A＝宛先・承認者・申請先の候補から外す**。**B＝名簿・一覧・履歴・集計では出したまま**。
- 分類：**A** 宛先・承認者・申請先の候補（休職中は外す）／**B** 名簿・一覧・表示・集計（休職中も出す）／**C** 判断がつかない（理由つき）。
- 「B（段6）」＝シフトの表・当番・勉強会の名簿。休職中は**週の期間で**外す予定（計画の段6）なので、`on_leave` の一律の絞り込みは入れない。
  件数は B に数える。
- 行番号は 2026-10-19 の master（532aeeac）時点。

## 数え方の注意（「約124か所」との違い）
- `client/src` で文字列 `is_active` が出てくるのは **129行**（`grep -rn is_active`）。
  そのうち `profiles` の在籍を**条件に使っている**のは下の表の行。残りは
  ①型の定義 ②コメント ③`profiles` ではない表の `is_active`（定期リマインド `board_scheduled_reminders`）④書き込み、で「対象外」に分けた。
- 計画の「124か所」は SQL や別の書き方も含めた概数と思われる。**画面側で `.eq('is_active', true)` と書いている所は 28か所**だった。

### 2-3. 気づいたこと
- 🚨 **申請先（休暇の approver_id／approver2_id、残業・勤務変更の reviewer_id）が承認者かどうかを確かめるトリガーは今ひとつも無い**
  （`role_is_*(new.…)` の形を探して0件）。計画の「申請先に休職中の人が入るのを DB で止める」は新しく作ることになる。

  休職で `not on_leave` を足すとき、在籍の扱いもそろえるか決める（退職者は role_id を持ったまま＝申請期間中の退職者が is_approver で true になりうる）。
- **notify_safety_urgent を C にした理由**：安否確認で「助けが必要」と答えた人のことを上長に知らせる。休職中のマネージャーは駆けつけられないので外す、とも読めるが、
  計画は「安否確認・緊急は必ず送る」。これは休職中の人**が受け取る**側の話で、休職中のマネージャー**へ**送るかは決まっていない。

  計画の「RLS のラッパーだけに `not on_leave`・`role_is_*` 本体は変えない」だと、**この4本には休職が効かない**。

## 4. 1か所で判定するための提案（たたき台）

1. **DB に「宛先・承認者になれる人」の関数を1本**（例 `is_assignable(uid)` ＝ `is_active and not on_leave`）。
   - `resolve_role_recipients`・`profile_ids_for_roles`・`set_board_approver_ids`・`retire_checklist_notify`・`shift_adjust_notify_plan_due`・`retire_apply` の付け替え先は、
     今の `p.is_active = true` をこの関数（または同じ式）に置き換える。これで 2-2 と 3-1 の宛先は**自動で**外れる。
   - RLS のラッパー（`is_manager_plus()`・`is_leader()`・`is_leader_plus()`・`is_approver()`・`is_board_approver()`・`is_org_wide()`）にも同じ判定を入れる。
     今は在籍を見ているものと見ていないものが混ざっているので、ここでそろえる。
   - 🚨 `role_is_*(uid)` を直接呼ぶ Edge Function 4本（3章のまとめ）は、ラッパーではなく同じ判定の RPC（例 `role_is_manager_plus_active(uid)`）を呼ぶように直す。
2. **画面は lib に宛先用の絞り込みを1つ**（例 `lib/assignable.ts`）。
   - `profiles` から候補を引く所（1章 A1〜A15）は、`.eq('is_active', true)` を `withAssignable(query)`（`.eq('is_active', true).eq('on_leave', false)` を足すだけ）に置き換える。
     名前（is_active ではなく assignable）で「宛先用」と分かるようにし、B の名簿の所と混ざらないようにする。
   - ESLint に「`profiles` を `acts_as`・`is_approver`・`is_manager_plus`・`is_board_approver` で絞るときは `withAssignable` を通す」ルールを足すと、今後の足し忘れを防げる
     （役職名の直書きを禁止したルールと同じやり方）。
   - 1か所の一覧を名前の表示にも使っている所（A14 シフト調整・A15 有休奨励日）は、**候補だけ**絞り、名前引きは別にする。
3. **本人あての自動のお知らせ（A'）** は、送る関数ごとに「休職者の使える機能」を見る。判定は `user_has_feature_permission` に休職の足し引きを入れて1本にする案（C の判断が要る）。
4. **申請先のトリガー**（今は0件）を新しく作るときも、1 の関数を使う。
5. 外さないもの（B）は触らない。シフト系（B（段6））は段6で「週の期間」の判定を別に作る。安否確認（B48・cancel_safety_check・safety-check-send の宛先）は必ず届ける。

### 決めてもらうこと（C の一覧）
- 1章 C1 連絡板の宛先プリセット（「マネージャー・リーダー」など役職あてに休職中の人を入れるか）
- 1章 C2〜C6 申請の依頼・パートへの休暇の依頼・勤務変更の代理と予定一覧（休職者の機能の初期値と合わせて決める）
- 1章 C7・3章 remind-scheduled 定期リマインドの名指しの宛先（選ぶ段階で外すか、送る段階で外すか）
- 1章 C8 精算の「指示した人」の選択肢
- 2章 notify_safety_urgent（休職中のマネージャーにも「助けが必要」を送るか）
- 2章 user_has_feature_permission に休職の機能を入れるか
- 3章 announcement-notify／announcement-remind（管理者からのお知らせを休職中の人にも送るか）
- 3章 remind-overtime-pending-review（休職中の申請先の催促を誰にも送らなくなる件）
