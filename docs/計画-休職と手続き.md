# 計画：休職の登録と、入社・退職・休職の手続き（2026-10-17 ユーザー確定・一問一答）

🚨 公開リポジトリ。個人名は書かない。
作るのはレビュー（UI/UX・シニアエンジニアの2体）のあと。

## きっかけ
- 「在籍外」は退職と入社予定しかなく、休職の扱いが無い。休職のときは［退職］を押すか何もしないかしかなかった。
- 入社・退職の手続きのリストは、全部済むとマネージャーが開く入口が無くなる（ホームの案内とベルは「残りがあるとき」だけ）。
- 全部済んでも「完了」のお知らせが無い。

## 決まったこと

### 休職
1. **ログインできる**。`profiles.is_active` は true のまま（退職者・入社予定とは別の扱い）。
2. **使える機能**＝休職者の「基本の機能」＋人ごとの足し引き。
   - 基本の機能は権限管理に「休職者」の列を足して決める（退職者の列と同じ形）。
   - 初期値：連絡板・FAQ・交通費・残業申請・勤務変更 だけオン。休暇・出張報告・備品・場所予約・勤怠カレンダーはオフ。
   - 実際に使えるのは「基本（＋人ごとの足し引き）でオン」かつ「休職前の役職で使えていた機能」（退職者と同じ決め方）。
   - **役職としての画面（受理・確認・手続き・ほかの人の休職の表示）は使えない**。見えるのは自分のことだけ。
     どうしても必要な人は、管理者が「その人だけ」で足せる。
3. **登録**：管理画面 → ユーザー → その人の行の［休職］。管理者だけ（マネージャーは見るだけ）。
   - 開始日（必須）・復職予定日（「未定」も選べる）・使える機能（［基本どおり］／［この人だけ変える］）。
   - その人あての**受理待ち**があれば黄色い枠に一覧を出し、1件ずつ付け替え先を選ぶ（「付け替えない」も選べる）。
     付け替えたら申請者と新しい申請先にベル。**自動では動かさない**（退職は自動で「管理者」へ。休職は戻る前提のため）。
   - 登録後、ユーザー一覧の名前の横に灰色の札「休職予定 10/20〜」→ 開始日から「休職中（復職予定 未定）」。［休職を修正］［復職］。
4. **切り替え**：開始日に自動で休職中に。復職予定日に自動で戻す。未定の人は管理者の［復職］で戻す。延びたら管理者が日付を直す。
   ［復職］は予定日より早く戻るときにも押せる。
5. **見える人**：「休職中」と分かるのは管理者・マネージャー以上・本人だけ。ほかのスタッフには何も出さない
   （承認者の候補や宛先から静かに外れるだけ）。マネージャー本人が休職したときも同じ（ほかのマネージャー以上と管理者には見える）。
6. **外すもの**：承認者の候補（休暇の1人目・2人目、残業・勤務変更の申請先、備品の承認者など）／毎朝のお知らせ・役職あてのお知らせの宛先。
7. **シフトの表**（勤務表・大人／こどものシフト表・管理部シフト表）：休職の期間に入る週からは出さない（予定に入れられない）。
   勤務表の登録は残すので、復職したら元の勤務がそのまま戻る。
8. **スマホのお知らせ（プッシュ）**：休職中は既定で送らない（ベルだけ）。**安否確認・緊急は必ず送る**。
   人ごとに「送る／送らない」。決めるのはチェックリストの項目（下の 10）で、本人も「設定」で変えられる。
9. **本人のホーム**：うすい灰色の1行「現在、一部の機能のみご利用いただけます。」（休職の間はずっと出る・閉じられない・日付は出さない）。

### 休職のチェックリスト
10. 入社・退職と同じ部品。「休職」のタブ。**「休職に入るとき」と「復職するとき」の2つ**に分ける。
    - 初めから入れておく項目（入るとき）：
      - 「スマホのお知らせの希望を本人に確認する」［送る］［送らない］ … 選んだものがそのままその人の設定になる（初めは「送らない」）。
        本人が「設定」で変えたら、こちらの表示も変わる。
      - 「休職中に使える機能（連絡板・交通費など）を本人に伝える」
    - 残りのお知らせ：開始日・復職日のそれぞれ 7日前・3日前・前日・当日（入社と同じ・日数は通知設定で変えられる）。マネージャー以上と管理者・ベルだけ。

### 入社・退職・休職の手続き（3つ共通）
11. 全部済んだら「✅ ◯◯さんの◯◯の手続きがすべて完了しました」をベルだけ（マネージャー以上と管理者）。
12. マネージャーの入口：上のナビにボタン（マネージャー以上と管理者だけ）。ナビの並び替え（`docs/計画-ナビの並び替え.md`）では並べ替えできる部分に入れ、初めは FAQ の手前。
13. マネージャーも項目の編集を全部できる（管理者と同じ：追加・名前・並び・必須・終了・選択肢）。
    退職日・休職の登録・入社予定の登録など、項目以外の設定は管理者だけのまま。

## 作り方のたたき台（レビューで直す）
- 表 `staff_leaves`（1人が何回でも休職できるので行で持つ）：user_id・start_date・return_date（空＝未定）・状態（予定／休職中／終了／取消）・
  push_on（既定 false）・機能の足し引き（足す／引く の feature_key の配列）・登録した人・終えた人と日時。
- 「今日休職中か」の判定は DB の関数1本（画面・お知らせの宛先・承認者の候補・シフトの表・push-dispatch が同じものを見る）。
- 毎晩の処理（退職・入社と同じ cron）で開始・復職を切り替え、手続きの残りのお知らせを出す。
- 画面の権限：hooks/useAuth の effectivePerms（退職者の絞り込みと同じ1か所）に休職の絞り込みを足す。役職の属性も休職中は false。
- 承認者の候補・宛先：`is_active=true` で絞っている所（lib/notificationDispatch・resolve_role_recipients・profile_ids_for_roles・
  毎朝のお知らせの Edge Function・各画面の申請先の一覧・備品の承認者のトリガーほか約20か所）に休職を足す。🚨 書き写さず1か所で判定する方法をレビューで決める。
- プッシュ：push-dispatch（共用）で、休職中で push_on=false の人には安否確認・緊急以外を送らない。
- チェックリスト：表 `leave_checklist_items`（phase＝入るとき／復職するとき）・`leave_checklist_checks`（休職の行ごと）。
  lib/staffChecklist の CHECKLIST に3つ目として足す。スマホのお知らせの項目は auto_key で staff_leaves.push_on とつなぐ。

## レビューの結果（2026-10-17・UI/UX とシニアエンジニア・主な指摘は自分でコードを見て裏取り）
### 作り方で守ること
- 🚨 my_access_state に新しい mode を足さない（_shared/callerGate.ts は mode が staff と retiree_grace だけ通す＝休職中の人の交通費・残業のあとの通知が黙って 403 になる）。
  mode は staff のまま、休職の状態は useAuth の loadProfileOnce（profiles）で読み、端末の控え（authCache）にも入れる（入れないと全部のナビが一瞬出る）。
- 承認者・宛先から外す：profiles.on_leave（boolean）を足し、staff_leaves のトリガーと毎晩 0:00 JST の cron の両方から leave_sync() で更新（当日開始ならその場で切り替わる）。
  SQL：resolve_role_recipients・profile_ids_for_roles・set_board_approver_ids・notify_event に not on_leave。
  サーバーの止め：RLS のラッパー is_manager_plus()／is_leader_plus()／is_approver()／is_board_approver()（auth.uid() 版）に not on_leave。🚨 role_is_*(uid) 本体は変えない。
  画面：.eq('is_active', true) は124か所。「宛先・承認者（休職を外す）」と「表示・名簿（休職中も出す）」を先に一覧で仕分ける（段0）。lib に1か所の絞り込みを作る。
- 申請先に休職中の人が入るのを DB で止める（休暇の approver_id/approver2_id・残業と勤務変更の reviewer_id の insert と、値が変わった update）。前の申請から申請先を戻す所があるため。
- プッシュ：send-push を直接呼ぶ関数が9本ある。判定の関数1本を send-push と push-dispatch の両方で使う。緊急かどうかは push-dispatch の isUrgent（urgent・safety:）にそろえる。
  🚨 既存のミュート（保留して後で届ける）に混ぜない。休職は「送らずに捨てる（ベルは残る）」。
- staff_leaves の状態（予定・休職中・終了）は日付と終えた日時から計算する（取消だけ列で持つ）。同じ人に終わっていない休職は1行まで。退職の確定・復活のときに休職を閉じる。
- 「受理待ち」の対象は退職の付け替え（retire_apply）と同じ定義を SQL 関数1本にして共用。
- useAuth の realIsAdmin は全部の can* を素通りさせる→休職中は false（または管理者アカウントには休職を登録させない）。役職プレビューに「休職者」を足す。
- 休職の日付は staff_leaves に置き、RLS は本人・マネージャー以上・管理者だけ（profiles は全員が読めるため）。シフトの表には期間だけ返す SECURITY DEFINER の関数。
- シフトの表は週の期間で判定（isShiftRosterMember は日付を見ない）。シフト調整の代わりの候補からも外す。
- 本人あての自動のお知らせ（有休奨励日・締め日など）も休職の機能で絞る（user_has_feature_permission）。
- チェックリスト：lib/staffChecklist の CHECKLIST は「profiles の行1つ＋日付の列」が前提→先に「対象（休職の行・phase）」を持てる形に直す。チェックは unique(leave_id, phase, item_id)。
  マネージャーが項目を編集するには items の RLS を is_admin() から広げる（退職・入社も同じ）。
  スマホの項目は push_on（値）と確認した日時を分けて持つ（「まだ聞いていない」と「聞いて送らない」を分ける）。本人の「設定」も同じ RPC を通す。
- 「全部済んだ」のベルはチェックのトリガーで判定し、記録で1回だけ。休職は「入るとき」「復職するとき」で別々に出す。
- 新しい関数はすべて anon を revoke して実測。順番：① DB → ② send-push・push-dispatch（共用・git pull・deno check）→ ③ 画面。

## 段1（入社・退職の手続き）の2回目のレビュー（2026-10-17）
- 「全部済んだ」はチェックの追加だけでなく、項目の変更（必須を外す・終了）でも起きる→ checks の after insert と items の insert/update/delete の両方から、同じ SQL 関数（例 checklist_remaining(kind, uid)）で判定。
  残りの数え方は今2か所（lib/retire.ts の retireRemaining と朝の通知）。画面からも rpc で呼べる形にしてこれ以上増やさない。
- 🚨 バックフィル：入社日（hire_date）は消さない列なので、過去に入社した人が全員対象のまま。出す前に、すでに全部済んでいる人の「送った」記録を入れておく（入れないと最初の変更で全員分のベルが飛ぶ）。
- 🚨 初めてのログインで自動で済みになる項目は auth.users のトリガー（notify_first_login）の中で書いている→完了を調べるトリガーは security definer・中身全体を exception when others で受ける（落ちるとログインが失敗する）。
- 「1回だけ」の記録は unique(kind, user_id, その時の日付)・on conflict do nothing。外して付け直し＝送らない／退職の取消のあと別の日付で登録し直し＝もう一度送る。
- items の書き込みのポリシーを分ける：追加・変更＝is_manager_plus()／削除＝is_admin() のまま／auto_key は管理者以外が触れない。画面は isAdmin を canEditItems（isAdmin || isManagerPlus）に分ける。
- マネージャーの編集で［必須］［隠す］［追加］が押した瞬間に保存され確認が無い→その場で影響を出して確かめる（「必須にすると、手続き中の2人の残りが1件ずつ増えます」など）。
  見出し「チェック項目（管理者のみ編集できます）」を直す・「最終変更：名前 日時」・スマホで［削除］を離して右端に・押せる大きさ 44px。
- 完了のベルの行き先は ?kind=…&person=id（済んだ方が隠れていても出して光らせる）。済みを押した本人には送らない。
- 📋 手続きのボタンは「試してから広げる」切り替えの対象にしない（マネージャー以上だけ・独立して出せる）。新しい通知は notification_settings に宛先の行を入れてから有効。
- （2026-10-17 ユーザー確定 A）全部済んだあとで必須の項目が足されたら、その人は「残り」に戻る（一覧にまた出る）。「完了しました」のベルはもう一度は出さない。
  退職を取り消して別の日付で登録し直したときは、新しい手続きとしてもう一度出す。

## 段0（仕分け）のあとの一問一答（2026-10-19 ユーザー確定）
仕分けの結果は docs/計画-休職-段0-仕分け.md（画面で外す所15・出す所48・決める所8）。
- 連絡板のお知らせ：休職に入るとき、本人に「連絡板のお知らせを受け取るか」を聞く（休職のチェックリストの項目・スマホのお知らせの希望と同じ形・初めは「受け取らない」）。
  - 受け取る人：今までどおり「正社員」の欄。まとめて選ぶ（全員・正社員など）にも入る
  - 受け取らない人：正社員の欄から外れ、別の「休職中（お知らせを受け取らない方）」の欄。まとめて選ぶには入らず、1人ずつチェックしたときだけ送る。
    この欄はマネージャー以上と管理者の画面だけ。ほかのスタッフの宛先選びには出さない（休職中と分かるのはマネージャー以上・管理者・本人だけの決まり）
  - 途中で変えられる：本人が「設定」→ 通知の欄（休職中の間だけ1行・「休職」という言葉は使わない・「連絡板のお知らせ（まとめて送られるもの）」）／
    マネージャー以上と管理者が手続きの「休職」のタブで押し直す。両方とも同じ値（チェックリストの表示も変わる）
  - 「受け取る」にした時点からまとめて送るものに入る。受け取らない間に送られたものはあとから届かない。1人ずつ選んで送ったもの・安否確認・緊急はいつも届く
- 申請の依頼の相手（C2）：休職中の人は、休職中に使える申請の依頼だけ相手に出す（残業は出す・休暇は出さない）
- パートの方への休暇申請の依頼とその件数（C3・C4）：休職中の人は出さない（休暇が使えないため・一覧と件数を同じ条件に）
- 勤務変更を代わりに出す相手・予定の一覧（C5・C6）：今のまま出す（休職前の日の報告がまだのときに上長が代わりに出せるように）
- 定期リマインドの名指しの宛先（C7・remind-scheduled）：休職中は送らない。管理画面の選ぶ画面には「名前（休職中）」と出したまま残す（復職したらまた届く）
- 精算の「指示した人」（C8）：休職中の人は出さない（休職前の分は管理者が直せる）
- 安否確認の「助けが必要」（notify_safety_urgent）：休職中のマネージャー以上には送らない（ほかのマネージャー以上・管理者には届く）。本人の安否確認はいつも届く
- 本人あての自動のお知らせ：休職中に使える機能のものだけ送る（有休奨励日の回答のお願いは送らない）
- 締め日のお知らせ：働いた日がある給与期間（前の月の16日〜その月の15日）だけ送る。期間がまるごと休職中なら送らない。
  例 11/1 休職・3/1 復職 → 11/14 は届く・12/14〜2/14 は届かない・3/14 から届く。休職の開始日・復職日から自動で判断（退職者の最後の申請期間と同じ考え方）
- 管理者からのお知らせ（announcement-notify／announcement-remind）：休職中で連絡板を「受け取らない」人には、スマホの通知・ベルを送らない。ホームの帯は出す（開いたときに見える）。
  復職したら「過去のお知らせ ›」で読み残しを見られる（掲載が終わっても未確認は上に「まだ確認していません」・今ある仕組み）。「受け取る」人には今までどおり届く
- 受理がまだの催促（remind-overtime-pending-review ほか）：申請先が休職中なら本人には送らず、経理（管理者）に回す（［代わりに受理］か付け替え）。付け替えなかった申請が誰にも気づかれず残らないように
- これで段0の「決めてもらうこと」は全部決まった（user_has_feature_permission は「本人あての自動のお知らせ」の決まりで休職の機能を入れる）

## 段3の1（DB の土台）の2回目のレビュー（2026-10-19・UI/UX とシニアエンジニア）と一問一答（ユーザー確定）

  → enforce_overtime_self_confirm は休職中でも役職で判定／overtime-approve・休暇の受理の update ポリシー・safety-check-send・receipt-signed-url の role_is_* は休職中を断る（初めての登録の前に）

- ［取り消す］は始まる前（予定）だけ。始まった休職は［今日から復職にする］で終える（期間の記録を残す）。日付の間違いは［休職を修正］
