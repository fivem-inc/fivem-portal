# 計画：残業の「表入力で全部」と「まとめて申請（スマホ）」（2026-09-29 起案・未実装）

きっかけ：リーダーの森本先生「残業申請も交通費のようにまとめて送信したい。特に事前申請」「スマホでもまとめて申請したい」。

## ✅ ユーザーの決定（2026-09-29・蒸し返さない）
- スマホは**交通費と同じ「箱」方式**（1日分を入れて［＋ 申請リストに追加］→［複製］で日付・時間を変えて追加→［申請する（◯件）］）。
  カレンダーで複数日を選ぶ案（案X・案Z）は「内容を日ごとに変えたい」ので採らない
- 残業ページに**［まとめて申請］タブ**を新しく作り、**マネージャー・社長・管理者だけ**で試す。事前申請も**事後報告も**入れられる
- **まず表入力（パソコン）で全部の種類を出せるようにする**。1行に収まらない入力は**その日の下に2行目**を開いて入れる
- 問題なく動けば、いつものフォームの「新しく出す」部分を［まとめて申請］に差し替える。
  実績報告・差し戻しの再提出・修正は「履歴」から1件を開いて直すものなので、1件分の画面として残す
- 差し替えた古い部分は、2〜4週間の猶予のあと消す（git に残る）
- **差し替えたあとのタブの名前は元の［事前申請・事後報告］に戻す**（［まとめて申請］のタブは試しのあいだだけ）。
  タブは今と同じ2つ（［事前申請・事後報告］［履歴・実績報告］）で、中身が箱の形になるだけ。パソコンの［📋 残業申請「表入力」］は今までどおり

## ✅ 表入力の形（2026-09-29 ユーザー確定）
- **種類の選び方は案A**：「種類」の列に小さな選択［時間 ▼］を常に置く（時間／時間外調整休／振替休日／欠勤／打刻が遅れただけ。その日に使えないものは選べない）。
  時間の欄は時刻の入力だけ（1行を細く保つ）。見本：会話で提示した「3案」の案A

- 理由の文例ボタンは表入力には**足さない**。「開始が遅い／早く終わる理由」の4択は今までどおり必須（選ばないとその行はエラーで送れない＝1件フォームと同じ validateOvertime）

## ✅ 作り始める前の決定（2026-09-29 ユーザー確定）

- 表で新しい種類（終日・打刻ズレ・移動）を選べるのは、**表入力を使える人全員（リーダー以上）**

## 最終確認（2026-09-29・UI/UX とエンジニア。どちらも「作り始めてよい」）
- 手順0 は1件フォームだけ直した。表の通知の条件（OvertimeGrid.tsx 433）にも打刻ズレの除外が要る。表の再提出のベルは「事前申請／実績報告」と出て、1件フォームの「再提出」と食い違う
  → 手順1で「通知を送るか」と「ベルに出す名前」を lib の関数にして両方から呼ぶ
- 23505 の比べ方は下書きの理由と比べている（Grid 406-408）。打刻ズレは保存時に理由を書き換える（overtimeSubmit 482）→ **buildOvertimeRecord の結果**（差分・理由・種別・勤務地・振替元）で比べる
- 送る直前の読み直しの比較（sameGridReport・overtimeGrid 79-83）に押した事情（late/early_situation）が無い → 足す
- 下書きは `{...init, ...s}` で読むので項目を足しても古い下書きは壊れない。ただ、終日・打刻ズレに切り替えた行に時刻が残ると、開いたままの古い画面から「時間の申請」として送れてしまう
  → 切り替えたら時刻を空にする（またはキーを :v2 に）。状態が変わった日の下書きを捨てる数え方（Grid 226）に種類も入れる
- 🚨 訂正：欠勤の申請先チェックの判定そのものは lib にある（overtimeSubmit 273）。画面にあるのは「申請先がマネージャー以上か」を見る部分だけ（Page 1129）。表の申請先の型（Grid 13）に役職を足す
- 打刻ズレの時間帯（Page 988-996）は既存の toWorkSegments(normalSegs) と同じ式 → 新しい関数は作らない
- 調整休の二重計上チェック（Page 1247）は error を見ておらず、読めないと素通り → lib に移すとき「読めなければ止める」に変える（動きが変わる点として断る）
- 今日の行の事前／事後は入れた開始時刻で決めている（overtimeGrid 301-303）→ 終日・打刻ズレは時刻が無いので種類ごとの規則が要る（ユーザーに確認）
- 合計の帯（gridBalance）は送る行をすべて「申請中」で数える。欠勤の自己受理も申請中の件数に入る（表示だけの小さなずれ）
- ［まとめて申請］は日付が複数の給与期間にまたがる → 送信ループは期間に頼らず、行ごとに締め切りと元の申請を受け取る形に
- **出す回の分け方（1回＝1つの push）**：①手順1（lib への移動＋通知の判定）②手順2（送信ループ：計算だけの関数＋差し替えできる「書き込み係」）
  ③移動＋締め後の許可の依頼 ④打刻ズレ（ここで種類の列が初めて出る）⑤調整休・欠勤 ⑥振替休日（単独）
  各回：node の検算（旧い式を写した検算ファイルと新しい関数に数百通りを通して比べる・書き込み係を偽物にして送信ループを試す）→ 実機（1件フォームで確認画面まで出して送らずに閉じる／表で1件ずつ送る）
