# 計画：出張報告から残業申請・勤務変更をつくる（2026-10-14 ユーザー確定・一問一答）

## いまの運用と目的
- 出張（出張・園指導・試合の引率など）に行った日は、**全員**がその日の申請を出している。
  正社員＝残業申請（勤務地変更など）、パート＝勤務変更。シフトの時間内の出張でも「いつ行ったか」を残すため。
- シフトの前から行く人が大半だが、勤務の時間内の出張もある。
- 出張先では「出張報告」の［到着］［終了］を送っている（位置情報つき・上長へお知らせ）。
- **目的は手間を減らすこと**：出張報告をした人には、その日の申請がほぼできあがっていて、確認・修正して送るだけにする。

## 決まったこと
1. 出張報告（到着・終了）は今までどおり。
2. ［終了］を送った直後に「この日の残業申請（パートの方は勤務変更）ができています」と出し、押すと入力済みのフォームが開く。
3. フォームに入っているもの：日付・勤務地＝出張先・種類＝勤務地変更。
   - **開始・終わりの時刻は空欄**（入れないと送れない）。着いた時刻≠勤務の開始、終了の報告≠帰った時刻のため（ユーザー指摘）。
   - 到着・終了の報告の時刻と行き先は、フォームの上の黄色い枠に参考として出す。
   - **理由は空欄**（本人の言葉で書く・2026-09-10 の決まり）。
   - 時刻を入れてシフトより長ければ、残業・早出は今の判定どおり自動で付く。
4. そのとき出さなくても、残業申請・勤務変更のページに「出張の申請がまだの日」として残り、あとから同じ形で出せる。
5. 片方しか報告していない日（到着だけ／終了だけ）も「まだの日」に出す。ある方の時刻だけ参考に出す。
6. 泊まりがけ：到着の報告から次の終了の報告までの日を1日ずつ出す（途中の日は参考の時刻なし）。
   到着と終了が8日以上離れているときは報告し忘れとみなし、到着の日だけ。
7. 受理（正社員の残業申請）：**受理なしで確定するのは、次のすべてに当てはまるときだけ**（ユーザー確定 B）
   - 決定済みのシフト表（**大人の「出張」・こどもの「園指導」**）に、その人・その曜日の出張がある
   - 行き先が同じ（下の 9 の正式な名前で照らし合わせる）
   - 申請の時刻がシフトの時間内（残業・早出なし＝差分 0 の勤務地変更だけ）
   - その日に出張報告がある（証拠）
   それ以外（シフト表に無い・行き先が違う・時間外で残業になる）は今までどおり受理を通す。
   受理なしで確定したときは、上長へベルだけ（スマホなし）＝「予定どおりの実績は受理なし」（2026-10-13）と同じ扱い。
8. パートの方の勤務変更は、いつも確認を通す（通常と異なるため）。
9. シフト表の出張（大人）・園指導（こども）の行き先は、**出張報告と同じ行き先リスト（master_options trip_location_*）から選ぶ**。
   - シフト表に出す名前は**行き先ごとに1つの短い名前**（例：上京陵和園→陵和園）。シフト画面のその場で直せる。直すとその行き先のマス全部が変わる。
   - いま入っている大人6件・こども4件は、対応する行き先の案を並べてユーザーに確かめてから入れ直す。

## 作り（案）
### DB
- 短い名前：行き先リストに `short_label`（master_options に列を足すか、別表 trip_location_labels）。
- シフト表の項目に正式な行き先：kids_shift_items に `trip_location`（master_options の value）。表示は short_label → なければ value。
- 残業申請・勤務変更に「出張から作った」印：overtime_reports / shift_reports に `from_trip_date`（または trip_report_ids）。上長の画面に「出張報告から」と出すため。
- 受理なしの判定は DB の関数（overtime_confirm_trip_rostered）：上の 7 の条件をサーバーで確かめる（画面の判断に頼らない）。
  enforce_overtime_self_confirm に、予定どおりの実績（app.ot_as_planned）と同じ形で印を足す。🚨 本番の実定義から起こす
- 「まだの日」の一覧：関数 my_trip_pending_days(from, to)（本人の出張報告の日 − 申請がある日。泊まりの展開もここで）。

### 画面
- 出張報告の［終了］の送信のあと：成功の知らせの中に［この日の残業申請を開く →］（正社員）／［この日の勤務変更を開く →］（パート）。
- 残業申請・勤務変更のページ：「出張の申請がまだの日」の一覧＋［出す］。
- フォーム：黄色い枠（📍 出張報告：到着 9:42（行き先）／終了 16:18）。時刻は空欄。下書きの持ち方は申請の依頼・打刻の確認と同じ（FormDraft に tripHint）。
- シフト表（KidsShiftPanel）：大人の出張・こどもの園指導の行き先を、リストから選ぶ（検索つき）＋短い名前の欄。

### お知らせ・FAQ
- 受理なしで確定したとき：上長へベルだけ（予定どおりの実績と同じ文の形）。
- 社内FAQ・残業申請と勤務変更の注意事項・出張報告の画面の説明を直す。

## レビューで足したこと（2026-10-14・UI/UX とシニアエンジニアの2体・主な主張はコードで確かめた）
### サーバー（受理なしの判定）
- 判定の関数は、画面が書いた値（diff_minutes・application_types・normal_shift）をそのまま信じない。
  いまの自己受理のトリガーは diff_minutes と application_types を信じており、フォームでは「いつものシフト」を手で直せる（normal_shift.manual_override）。
  シフトを出張の時刻に合わせれば差分0になるので、条件に次を入れる：
  - 本人の行・manual・reported・申請先が本人以外
  - application_types が location_change だけ／勤務地に「→」が無い
  - manual_override でない
  - 実際の勤務の全部が、サーバーで出したシフトの時間内
- シフト表：決定済みの項目だけ（cell_id があるもの。plan_cell_id は下書き）。
  曜日（day_kind）と有効期間で見る。対象は 大人×trip／こども×garden、active、is_none でないもの、本人が入っていること。
  🚨 シフト表は「毎週の型」で、日付ごとの予定ではない。会社休・休暇の日も型としては当たるため、止めるのは「その日の出張報告」と「差分0」。
- 行き先は「報告・申請・シフト表」の3つが同じときだけ。
- 印は app.ot_trip_rostered（予定どおりの実績の app.ot_as_planned と同じ形）。enforce_overtime_self_confirm は本番の実定義から起こす。
  履歴には「シフト表どおりの出張のため確定」と残す。
- 一般スタッフはシフト表を読めない（kids_shift_* は shift_patterns の権限だけ）。判定は SECURITY DEFINER の中で行う。
  画面で「受理なしになります」を前もって出すことはできない（送ったあとに結果を出す）。

### シフト表に行き先を持たせる
- kids_shift_items に trip_location_id（master_options.id）。名前（value）で持たない：区分をまたいで同じ名前があり、名前を変えると切れるため。
- シフト表の照合（kids_shift_cell_sig / payload_sig）には、値があるときだけ足す（split_time と同じ）。
  入れないと、開いている案の全部が「食い違い」になる。保存・複写・入力チェックの関数も本番の定義から直す。
- 短い名前は master_options.short_label（列）。直すのは shift_patterns の権限を確かめる SECURITY DEFINER の関数。
  表示で結び付けるだけで、class_name には書かない。シフト表の［保存］とは別に、確かめの枠を出してその場で保存する。

### 「まだの日」の決め方（DB の関数 my_trip_pending_days・本人だけ・anon を外す）
- 残業：その日に取消以外の申請があれば出さない（差し戻し中も出さない）。勤務変更：行が1つでもあれば出さない（取消を含む・重複で弾かれるため）。
- 出さない日：締めた給与期間（許可がある人を除く）・これから先の日・「定時」の記録（overtime_day_checks）がある日。
- 始まりの日を決める（それより前の出張は出さない）。
- その日に事前申請（requested / request_confirmed）があれば、新しいフォームではなくその申請の［実績報告］を開く。
- 到着と終了の組み合わせ（到着2回・終了だけ・行き先が違う・1日に2か所・日をまたぐ）は1つの関数で決める。日は日本時間で数える。

### フォーム
- 残業：日付を入れたときの「いつものシフトを入れる」に出張の分岐（勤務1・2とも空欄）。tripHint は下書きに入れ、日付を変えたら外す。
  勤務地は「その他」に入れる。黄色い枠は打刻の確認の枠とそろえ、シフトも並べる。
  「到着・終了は送った時刻で、勤務の開始・終わりではありません」と書く。片方だけの日は「終了の報告なし」と書く。
  学校の勤務もある日は［＋勤務を追加］で分ける案内。
- 勤務変更（パート）：手がかりは prefill に持たせる。今の「カレンダーの予定から」の文と、下書きを黙って上書きする穴（既存）も直す。
- from_trip_date は表示だけ（判定には使わない）。表入力と共用の buildOvertimeRecord では既定 null、送り直し・実績報告で消さない。

### 画面の置き場所と文
- 勤務変更の「未報告の一覧」はマネージャー以上にしか出ない（canShiftReportTodo）。出張の「まだの日」はパートにも必ず出す。
- 同じ日を2回出さない：勤務変更はカレンダーの予定と1つの一覧にまとめ、行ごとに「出張報告から」。残業は申請の依頼がある日は依頼を優先。
- ボタンは［内容を確認 ›］（［出す］は「送信」と間違えるため 2026-10-05 に改名済み）。見出し「📋 出張の申請がまだの日（2件）」。締め切りを添える。
- 残業は［事前申請・事後報告］タブのフォームの上。件数は履歴タブの数字に足さない。
- ［終了］のあと：緑の成功の知らせの中に「10/20（月）の出張は、残業申請で出せます。開始・終わりの時刻を入れて送るだけです。［10/20（月）の残業申請を開く →］［あとで］」。
  ［あとで］の下に「残業申請のページにも残ります」。もう申請があれば［履歴で見る →］。下書きの「置き換えますか」は移った先で。
- 泊まりがけは1つにまとめて見せる（├ 10/20 到着／├ 10/21 泊まりの間／└ 10/22 終了）。8日以上離れたら「終了の報告が見つかりません」と書く。
- 上長の画面：「📍 出張報告から」の札・到着と終了の時刻・行き先・受理が要る理由（シフト表に出張がない／行き先が違う／シフトより長い）。
- 送ったあと：「シフト表どおりの出張のため、受理なしで確定しました」／「◯◯さんの受理を待ちます」。
  上長へのベル：「🕐 ◯◯さんの10/20（月）の出張（陵和園）はシフト表どおりでした（受理は不要です）」。
  ベルだけ・新しい event_key は作らない（「設定が無い＝全員」の罠）。Slack・Google カレンダーはいつもどおり。

### ユーザーに決めてもらうこと（一問一答で聞く）
1. ✅「まだの日」の一覧を出し始める日 → 機能を出す日から（それより前の出張は出さない・2026-10-14 ユーザー確定 A）。
   日付は app_settings に持ち、出す日に入れる
2. ✅ シフト表で受理なしに数える役割 → 役割に関係なく、その枠に入っている人は全員（2026-10-14 ユーザー確定 A）
3. その日にシフトが無い日の種類（勤務地変更ではなく休日出勤にするか）
4. 正社員・パート以外の雇用形態（契約など）は残業申請と勤務変更のどちらにするか
5. 表入力・まとめて申請でも、出張の受理なしを効かせるか
6. 同じ園が「出張」と「園指導」の両方のリストにあるとき、短い名前を区分ごとに持つか
7. 区分が「その他」や自分で入れた行き先でも、申請への案内を出すか（受理なしにはならない）

## 気をつけること
- 出張報告の時刻は「送った時刻」。参考にだけ使い、申請の時刻には入れない。
- 申請は本人×日付で1件。すでに申請がある日は「まだの日」に出さない（取消・差し戻しの扱いは要確認）。
- 書きかけの下書きを黙って上書きしない（申請の依頼と同じ「置き換えますか」）。
- 行き先がフォームの勤務地の候補に無いときは「その他（自由入力）」に入れる。
